# 地图打卡与异步痕迹

> 状态：玩法 + 架构构思  
> 记录时间：2026-09-12  
> 来源：与作者的讨论  

---

## 一、一句话

世界是一张**可探索的地图**：你**经过**某地会自动**打卡**；链接颜色区分「来过 / 没来过」。  
你在某地留下的**痕迹**，后来的玩家能看见——**不必同时在场**，只有先后顺序。  
至于背后是一台服务器还是很多台：**玩家先感觉是一个世界**；运维按负载再拆，见 §五。

---

## 二、打卡地图：来过就会变

### 2.1 体验目标

像旅行 App 的足迹，或文字冒险里的地点树：

- 玩家进入、经过某地点 → **系统自动打卡**（无需额外点「签到」按钮，减少操作负担）
- 地图上通往各处的**链接**用颜色区分状态，例如：
  - **未到过**：冷色（蓝 / 青绿）— 「还没踏足」
  - **已到过**：暖色或褪色（琥珀 / 灰绿）— 「你来过这里」
  - **当前所在**：高亮 — 「你在这里」
- 再次打开地图：一眼看出探索广度，**不强迫清图**，只是视觉反馈

### 2.2 打卡规则（建议）

| 项目 | 建议 |
|------|------|
| 触发条件 | 页面加载该地点 ID，或从邻接地点**合法移动**进入 |
| 是否可重复打卡 | 只记**首次到达时间**；再次经过可更新「最近到访」但不刷奖励 |
| 数据存哪 | 服务器：`user_id + location_id + first_visited_at` |
| 与成就 | 可挂钩 §02 成就门槛（如「首次抵达灰烬港」），庆祝信进邮箱 |
| 与主线 | **无**；打卡不解锁「必做下一关」 |

### 2.3 地图形态（网页文字向）

不必先做 2D 瓦片大地图，MVP 可以是：

```
        [ 潮灯港 ] ← 你在这里（高亮）
           /    \
    [ 旧栈桥 ]   [ 商会街 ]
   （已到过）    （未到过·蓝）
```

- **节点** = 地点（百科 ID，与 `01` 世界条目一致）
- **边** = 可通行的链接（点击跳转）
- 后期可加：区域折叠、距离/危险度文字、小地图缩略图

## 三、异步痕迹：先来者留痕，后来者看见

### 3.1 和「同时在场」的区别

| | 传统 MMO 同图 | 本作（异步痕迹） |
|--|----------------|------------------|
| 时间 | 同一时刻多人同场景 | **有先后顺序**，不必同时在线 |
| 看见什么 | 实时模型、位置 | **留下的记录**：留言、标记、轻量互动残留 |
| 技术压力 | 同步、广播、分线 | **写一次、读 many**；更像留言板 + 世界状态 |
| 氛围 | 热闹、拥挤 | 幽径、「有人来过」的孤独感或温情感 |

玩家 A 周二在「旧栈桥」留了一句粉笔字；玩家 B 周五路过，能看见 A 的痕迹（及更早的人留下的）。

### 3.2 痕迹可以是什么（待产品裁剪）

不必一次全做，按**轻 → 重**排列：

| 层级 | 痕迹类型 | 示例 | 备注 |
|------|----------|------|------|
| L0 | **系统留痕** | 打卡记录本身（「127 人曾到过」） | 聚合统计，无 UGC 风险 |
| L1 | **轻标记** | 脚印图标、小旗、「我来过」 | 低成本，防 spam 限次数 |
| L2 | **短留言** | 粉笔字、钉在地点的一句话 | 需审核 / 敏感词 / 举报 |
| L3 | **轻互动残留** | 摆一朵花、点一根蜡、改动物理状态（门已推开） | 服务器记地点状态，后来者看见 |
| L4 | **订单残留** | 「此处曾有人完成过护送单」匿名条目 | 与商单系统挂钩 |

**原则**：痕迹挂在 **地点 ID** 上，不绑定「哪台物理服务器」；后来者读的是**共享世界状态**。

### 3.3 边界与馆规

- **不保证实时**：B 看不见 A 正在输入的字，只看见 A **已提交**的痕迹  
- **可衰减**：旧痕迹可淡出、归档，避免地点变成垃圾堆（馆规 + 容量上限）  
- **订阅前零推送**：新痕迹 **不弹窗**；玩家到该地点或打开地图时才看见  
- **与点菜式一致**：痕迹是探索的副产品，不是系统派的社交任务

## 五、服务器架构：分组？还是合成一个大世界？

> **诚实前提**：我们还没大规模维护过游戏服务器，上线后会发生什么要看真实负载。  
> 下面不是定论，是**先让玩家感觉一致、运维以后好拆**的架构笔记。

### 5.1 先分清两层

```
┌─────────────────────────────────────────┐
│  玩家层：一个 MiraWorld，一张逻辑地图      │  ← 体验上尽量「一个世界」
├─────────────────────────────────────────┤
│  运维层：N 台机器、M 个进程、数据库副本    │  ← 可以很多台，玩家不必知道
└─────────────────────────────────────────┘
```

玩家不应被迫理解「我在 3 服还是 7 服」。  
打卡、痕迹、背包、订单 —— 都应绑 **用户 ID + 地点 ID**，而不是绑「物理机编号」。

### 5.2 三种常见模型（对照）

#### 模型 A：多服分组（传统分线 / 分 shard）

```
[ 1 服世界 ]  [ 2 服世界 ]  [ 3 服世界 ]
  玩家选服      数据隔离      痕迹不互通
```

| 优点 | 缺点 |
|------|------|
| 单服故障隔离 | **同地点痕迹被切碎**，异步足迹体验变差 |
| 早期单机扛不动时可硬拆 | 玩家要选服、朋友可能不在同一「世界」 |
| | 与「一个地方很多人先后留痕」叙事冲突 |

**适合**：强 PVP、同屏人数极多、世界本身就不共享的玩法。  
**不太适合**本作强调的「同一地点、先后顺序、看见前人痕迹」。

#### 模型 B：多机组成一个逻辑大世界（推荐方向）

```
          [ 负载均衡 ]
         /     |     \
    [API-1] [API-2] [API-3]   ← 无状态，可水平加
              |
        [ 共享数据库 / 缓存 ]
              |
    地点、打卡、痕迹、订单、背包  ← 同一套逻辑世界
```

| 优点 | 缺点 |
|------|------|
| 玩家感觉**只有一个世界** | 数据库与热点地点可能成为瓶颈 |
| 打卡、痕迹自然全局可见 | 需要一开始就把「地点 ID」设计对 |
| 加机器 = 加 API 实例，不改玩法 | 运维要比单机复杂（但可控） |

**适合**：网页文字、异步社交、订单托管 —— **与当前 MiraWorld 方向一致**。

#### 模型 C：按地图区域分片（折中，规模大时再考虑）

```
[ 灰烬港片 ]  [ 潮灯港片 ]  [ 北境片 ]
   各片可不同机器          跨片移动走网关
```

| 优点 | 缺点 |
|------|------|
| 单片人口与痕迹量可控 | 跨片痕迹、全图打卡统计要额外设计 |
| 比「每服一整张地图」更省 | 实现比模型 B 复杂 |

**适合**：单区域痕迹爆炸（例如某网红地点百万条粉笔字）之后，**按地点 hash 分片**，而不是让玩家选服。

### 5.3 推荐路径（从未维护过服务器时的务实顺序）

| 阶段 | 做什么 | 玩家感受 |
|------|--------|----------|
| **MVP** | 单机 API + 单库（现状可延续） | 一个世界 |
| **第一步扩容** | 前面加负载均衡，**多台无状态 API** 写同一数据库 | 仍是一个世界 |
| **热点优化** | Redis 缓存地点只读数据；痕迹分页加载 | 仍是一个世界 |
| **真的扛不住** | **按 location_id 分片**痕迹表，或按区域迁库 | 仍尽量一个世界；运维才看见分片 |

**不建议 MVP 就做「选服」** —— 会把打卡地图和异步痕迹的核心体验打碎。

### 5.4 和「很多服务器」的一句话结论

| 问题 | 建议答案 |
|------|----------|
| 分组还是合成一个大服？ | **逻辑上合成一个大世界**；物理上可以多台 API 共同服务 |
| 玩家要不要选服？ | **不要**（除非以后做竞技排位等特殊玩法） |
| 痕迹存在哪？ | **地点 ID + 时间序**，存在共享存储，不按物理机隔离 |
| 我们现在不知道会怎样？ | 正常；**先单库 + 地点模型设计对**，比过早分服重要 |

## 六、数据模型草图（实现时可参考）

```text
locations          id, name, region, links[]
user_visits        user_id, location_id, first_at, last_at
location_traces    id, location_id, user_id, type, payload, created_at
                   -- type: flag | chalk | flower | order_echo ...
                   -- 按 location_id + created_at 分页查询
```

- 打卡：`user_visits` 首次插入即变色  
- 痕迹：`location_traces` 插入后，该地点后续访问者可见（遵守衰减规则）  
- **所有 API 实例**读写同一套表 → 多机即「一个大世界」

## 七、MVP 可验证什么

1. **5～10 个地点**的节点地图 + 链接变色（来过 / 未到过）  
2. 进入地点 **自动打卡**，刷新地图颜色正确  
3. **L1 轻标记** 或 **L2 一句粉笔字**（任选其一）+ 后来者可见  
4. 痕迹列表分页，单地点上限（如最近 50 条）  
5. 问玩家：异步痕迹是否增强「有人来过」的感觉，而不吵？

## 八、待讨论

- [ ] 链接未到过 / 已到过的具体色板（无障碍：不只靠颜色，加图标或文字）  
- [ ] 痕迹要不要实名、半匿名（「一位行者」）还是全匿名？  
- [ ] 单用户单地点留言次数上限？  
- [ ] 痕迹是否可删（本人 / 管理员 / 举报后）？  
- [ ] 全图打卡进度要不要展示百分比（易变「清图强迫症」）？  
- [ ] 模型 B 单库瓶颈预估：日活多少时再评估模型 C？

## 九、小结

| 维度 | 选择 |
|------|------|
| 地图 | 节点 + 链接；**经过即打卡**；颜色区分来过与否 |
| 社交 | **异步痕迹**，非同屏；先后者看见先来者留的东西 |
| 服务器 | 玩家侧 **一个逻辑世界**；多机是无状态 API + 共享库，**不先做选服分线** |
| 未知 | 负载上来再按 **地点分片**，而不是重做「多服分组」体验 |

> 世界像一本被很多人翻过的书：你不是和他们在同一页上相遇，但你能看见页边的批注和折角。
