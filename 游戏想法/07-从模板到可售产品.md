# 从模板到可售产品：最值得讨论的一关

> 状态：核心难题（创作 + 包装）  
> 记录时间：2026-09-12  
> 来源：与作者的讨论  
> 定位：**全文最重要的问题之一** —— 用户如何用我们的 API/模板，做出**真实有内容、客户愿意付钱**的产品。

---

## 一、难题在哪：两扇门，不是一扇

整条链里，**最难的两步**往往不是宣发，而是：

```
┌─────────────────┐         ┌─────────────────┐         ┌─────────┐
│ ① 再设计 / 创作  │   →    │ ② 包装 / 上架   │   →    │ C 购买  │
│ （Blueprint）    │         │ （Product SKU）  │         │         │
│ 「有没有料」     │         │ 「愿不愿意点」   │         │         │
└─────────────────┘         └─────────────────┘         └─────────┘
        ↑                           ↑
    最难之一                    最难之二
```

| 阶段 | 在做什么 | 难在哪 | 失败长什么样 |
|------|----------|--------|--------------|
| **① 再设计** | 用 SDK/模板/API 编排**可玩的真实内容** | 空有原子不会讲故事；平衡、时长、验收 | 能跑但无聊；或死锁、奖励爆表 |
| **② 包装** | 把 Blueprint **变成顾客看得懂、愿意买的 SKU** | 标题、描述、定价、试玩、权益说明 | 内核还行但像系统日志；或价不对没人买 |
| ③ 宣发（可后置） | 让人看见 | 没前两步，宣发是空炮 | 点击进来不买 |

**系统能提供芯片和厨房；料和摆盘仍是人的事。** 本文专门讨论：平台怎样**降低①②的难度**，又不把「可售」变成「空壳上架」。

---

## 二、客户愿意为什么付钱？（先定验收标准）

在谈 API 之前，先定 **C 买单的理由**。数字商品在这里 ≈ **可消耗的体验权益**，不是纯图标。

| C 愿意付钱的条件 | 系统如何验证「真有内容」 |
|------------------|--------------------------|
| **能玩到一定时长/深度** | 沙盒跑通 + 最短路径时长 ≥ N 分钟 |
| **有明确交付物** | `deliverable`：N 次调查 / 一段剧情 flag / 配方解锁 |
| **可重复或可追溯** | 订单/库记录；不是一次性空跳转 |
| **值这个价** | 同类 SKU 行情 + 评价；2h 退款政策倒逼质量（`01` §20.6） |
| **信任卖家** | 店铺信誉、试玩片段、已购评价 |

**一句话：可售 = Blueprint 在沙盒里证明「有玩头」 + SKU 把玩头翻译成人话。**

## 三、① 再设计：用户如何用 API / 模板做出「有料」的 Blueprint

### 3.1 不要从空白开始：模板是「菜系」，不是「白盘」

方案方最怕：**SDK 原子列表甩脸上，不知道拼什么。**

建议分层：

| 层级 | 是什么 | 创作者做什么 |
|------|--------|--------------|
| **L0 原子** | `VisitLocation`、`DialogueChoice`、`Reward`… | 一般不直接面对 C |
| **L1 模板（菜系）** | 「调查包」「护送包」「收集包」「短篇叙事包」 | **选菜系 + 填参数** |
| **L2 Blueprint** | 一份可运行的完整方案 JSON | 在模板里换地点、对话、分支、奖励曲线 |
| **L3 SKU** | 商品壳 | 见 §四 |

**MVP 路径：**

1. 系统预置 **1 个菜系模板**（如「单地点调查」）  
2. 创作者只填：地点 ID、对话树、奖励、可玩次数  
3. 沙盒必须通过 → 才能授权给 B₂ 或自己上架  

后期再开放节点图；**先让「填模板就能卖」跑通**，比先造 IDE 重要。

### 3.2 模板里必须帮创作者回答的五个问题

每个官方模板自带 **需求卡**，强制填完才能提交：

1. **玩家来干嘛？**（目标一句话：找线索 / 护送信物 / 收集三件遗物）  
2. **玩多久？**（系统根据节点估算最短/最长路径）  
3. **赢什么？**（奖励在经济 cap 内；系统自动标红超标）  
4. **能玩几次？**（`grant: quest_run_token, count: N`）  
5. **凭什么值得买？**（给 B₂ 包装用的「卖点 bullet」— 从设计里自动生成草稿）

### 3.3 API / SDK 的真正分工

```
创作者写的          系统跑的（API）
──────────          ──────────────
选地点、对话、分支   VisitLocation 验收
定奖励数字           Reward 经济上限校验
定可玩次数           GrantToken 发放
定分账比例           EscrowSplit 成交时执行
```

创作者**不写服务器代码**；写的是 **在世界百科里已存在的 ID + 模板参数**。  
这样「真实内容」= **官方世界里有据可查的地点/NPC/物品** + **经校验的流程**。

### 3.4 工作流（B₁ 或一人兼 B₁+B₂）

```
选模板「调查类」
    → 从百科选 location / dialog / item（防编造）
    → 表单向导填参数（或节点图，后期）
    → 沙盒试玩（测试账号，不污染正式经济）
    → 系统红灯检查：死胡同 / 奖励超标 / 时长<3min
    → 通过 → 提交 Blueprint → 入库
    → 授权给 B₂（或自己就是 B₂）
```

详见 `01` §18.12；本文强调：**沙盒红灯是「有料」的最低门禁。**

### 3.5 内容从哪来？（模板解决不了灵魂）

API 解决 **能跑、能验收、能分账**；**灵魂**还要来自：

| 来源 | 做法 |
|------|------|
| **官方示例 Blueprint** | 系统自带 1～2 个高质量样例，可 fork 改 |
| **雇编剧** | Studio 发服务单买文稿，绑定到 `DialogueChoice` 节点 |
| **势力/NPC 官方包** | 拾遗院、商会提供「授权对话包」模板 |
| **玩家共创（后期）** | 征稿悬赏，最佳剧本进方案库 |

**模板降低结构难度；叙事质量仍要人写或买。**

## 四、② 包装：如何把 Blueprint 变成「愿意消费」的 SKU

包装不是骗点击，是 **把已验证的玩点翻译成购买决策**。

### 4.1 SKU 上必须有的字段（产品工作台）

| 字段 | 作用 | 常见翻车 |
|------|------|----------|
| **商品名** | 3 秒内懂卖啥 | 「BP-7f3a」类系统 ID |
| **一句话卖点** | 从 Blueprint 自动草稿 + 人工改 | 抄原子列表 |
| **预计时长 / 次数** | 「约 45 分钟 · 可玩 5 次」 | 不写，买完不知道干啥 |
| **标签** | 调查 / 恐怖 / 短篇… 进商城筛选 | 乱贴 tag |
| **封面 / 图** | 哪怕一张氛围图 | 默认灰图 |
| **试玩** | 第 1 节点或 10 分钟片段（可选 MVP+） | 无试玩贵价货难卖 |
| **价格** | 对照行情带 + 体量 | 随意定价 |
| **交付说明** | 「购买后库中增加 5 次委托入口」 | 含糊「获得物品」 |

### 4.2 包装与 Blueprint 的关系

```
Blueprint（内核，买家不可篡改）
    │
    ├─ royalty_rate、nodes、验收逻辑  ← B₁ 知识产权
    │
    ▼
Product SKU（外壳，B₂ 可改文案定价）
    │
    ├─ 名、图、描述、价、标签
    │
    ▼
商城列表页 → C 决策
```

**同一 Blueprint** 可被多个 B₂ 包成不同 SKU（不同名图价），像不同出版社出同一剧本的插图版/精装版 —— 但 **运行时一致**，防偷工减料。

### 4.3 包装阶段的系统辅助（降低②难度）

| 辅助 | 说明 |
|------|------|
| **自动摘要** | 从 Blueprint 生成「地点数、分支数、预估时长、奖励概要」 |
| **定价建议** | 按时长带 + 品类均价给区间（非强制） |
| **合规检查** | 描述禁夸大（「必掉神器」而蓝图没有） |
| **绑定校验** | SKU 只能绑已授权 `blueprint_id` |
| **预览库** | B₂ 自己先跑一遍再点上架 |

### 4.4 包装难在哪：不是技术，是「商品思维」

很多创作者会做关卡，不会写 **货架语言**。  
平台可提供：

- **包装模板**：「调查委托包」「剧情解锁券」「工匠配方包」三种货架版式  
- **示例对标**：同标签销量 Top 3 的 SKU 结构（匿名）  
- **必填卖点**：至少 3 条 bullet，其中 1 条必须来自系统生成的「事实」（如时长、次数）

宣发可以后置；**货架语言不合格不允许上架**，比事后没人买更省成本。

## 五、端到端：一个人从零到可售（最简故事）

**角色：小满，一人兼 B₁+B₂**

1. 打开 **方案工作台** → 选模板「灰烬港单点调查」  
2. 从百科选 `ashen_harbor`、`dialog_ash_01`，设奖励 50 币 + 10 声望，可玩 5 次  
3. **沙盒试玩** 12 分钟通关，系统绿灯  
4. 提交 Blueprint `BP-ash-01`，`royalty_rate` 留 0（自己包自己）  
5. 进 **产品工作台** → 绑 `BP-ash-01`  
6. 填 SKU：「灰烬港夜雾调查 ×5」、卖点、标签调查/短篇、价 80 灯油  
7. 系统校验描述与蓝图一致 → 上架全服商城  
8. 玩家 C 购买 → 库中 +5 次入口 → 玩完可评 → 小满分账  

**全程未写代码；写的是模板参数 + 货架文案。**

## 六、平台责任边界：我们管什么、不管什么

| 平台必须管（硬） | 平台不替做（软） |
|------------------|------------------|
| 原子组合合法、经济 cap、沙盒可跑通 | 文学好不好（交给市场评价） |
| SKU 与 Blueprint 交付一致 | 爆款选题（给行情参考即可） |
| 分账、退款、库权益 | 代写剧本、代做美术 |
| 死锁/零时长检测 | 宣发投放 |

**目标：让「及格可售」变容易，让「优秀爆款」仍靠创作者。**

## 七、分阶段开放（别一上来就做满 IDE）

| 阶段 | 创作者能力 | C 能买到什么 |
|------|------------|--------------|
| **P0** | 仅系统 | 系统预置 1 个调查包 SKU |
| **P1** | 填官方模板参数 | 若干「换地点/对话」的委托包 |
| **P2** | 模板 + 雇编剧服务单 | 带自定义文案的包 |
| **P3** | 节点图编排 | 更长分支、多结局 |
| **P4** | 新原子申请 + Studio 整游戏 | Steam 式完整 Game |

**最值得先讨论并做透的是 P0→P1**：证明 **模板 + 包装 → 有人买**。

## 九、小结

| 问题 | 答案 |
|------|------|
| 最难的两步？ | **再设计（Blueprint）** + **包装（SKU）** |
| API/模板干什么？ | 让内容 **能跑、能验、能分账**；从菜系模板填参，不从零写代码 |
| 怎么算「真实有内容」？ | 沙盒跑通 + 最短时长 + 明确 deliverable + 商城可核对描述 |
| 怎么算「愿意消费」？ | 包装翻译玩点 + 定价带 + 试玩/评价 + 库权益清晰 |
| 宣发？ | 重要但**后置**；前两步不过关宣发无效 |
| 我们先做什么？ | **P0→P1：一个模板、一套产品工作台、一条可购买闭环** |

> 模板是厨房的标准菜谱；Blueprint 是厨师按菜谱做出来的一道菜；SKU 是端给客人看的菜名与摆盘。  
> **客人买单，买的是吃到的体验，不是菜谱 JSON。**
