# 玩家职业与异步律师：馆规下的角色扮演

> 状态：社会规则 + 职业玩法构思  
> 记录时间：2026-09-12  
> 来源：与作者的讨论  
> 定位：许多**职业由玩家扮演**；游戏**不是严肃现实模拟**，但要有**可遵守的规则与氛围**。律师是首个详化的异步职业范例。

---

## 一、一句话

世界里的律师、厨师、信使……可以是**玩家**扮演的；  
律师须先通过一场**很简单的资格考**（愿意参加基本能过），再在**异步评审团**上阅卷——  
流程是：**用户举报 → 系统裁举报过不过 → 商家不服可申诉 → 律师团对照双方状纸与环境主题，投票支持谁**；没有同步法庭。

---

## 二、整体立场：像角色扮演，不是严肃仿真

| 维度 | 本作 |
|------|------|
| 现实法庭 | **不做**同步开庭、举证质证马拉松 |
| 规则与氛围 | **要做**——有馆规、有资质、有裁断记录 |
| 职业感 | 玩家「扮演」身份，系统给**硬边界**（能干什么不能干什么） |
| 与异步世界观 | 一致（`04` 信箱、`03` 痕迹、`05` 按需刷新） |

> 像剧团里的法官：戏服是真的，台词可简，但**不能坏了馆里的规矩**。

## 三、玩家可扮演的职业（谱系）

许多职能已在其他文档出现，此处归纳为**职业身份**：

| 职业 | 生活类比 | 主要文档 | 同步度 |
|------|----------|----------|--------|
| **食客** | 下馆子的人 | `02` | 异步 |
| **厨师 / 服务员** | 接单出活 | `02` `01` | 异步 |
| **行者 / 信使** | 跑腿外卖 | `01` | 异步 |
| **店主 / 原料商** | 进销存 | `01` `06` | 异步 |
| **方案方 / 产品方** | 研发与包装 | `07` `01` | 异步 |
| **律师** | 馆规裁断与合议 | 本文、`08` | **异步** |
| **（后期）审计、仲裁员、馆吏** | 查账、复核 | 待定 | 异步 |

**默认原则**：职业玩法 **错时友好**；不要求「全体律师同时上线」。

## 四、律师：资质与入门

### 4.1 为什么要有资质

律师能影响**他人账号、资金冻结、下架**等后果，门槛过低会毁环境（`08`）。  
但门槛过高又没人玩——故：

| 设计 | 说明 |
|------|------|
| **资格考** | 短卷，题量适中（概念上可称「馆规考」）；**偏常识与馆规阅读** |
| **难度** | **故意简单**——认真读帮助页与馆规，愿意参加**基本能过** |
| **目的** | 筛掉完全不看规则的人，而非筛天才 |
| **重考** | 未过可再考；冷却例如 24h（防刷） |
| **通过后** | 获得身份 **`注册律师`**，证书进角色卡 / 邮箱 |

### 4.2 资质边界（能做什么）

| 在资质内 | 不在资质内 |
|----------|------------|
| 在**合议台**对案件投「认同 / 不认同」票 | 私下代他人操作账号 |
| 撰写**评议摘要**（异步留言，供卷宗留存） | 保证胜诉、收现实货币 |
| 按馆规引用条款编号 | 改系统硬数据、绕过托管 |

违规 → 吊销律师资格 + 信誉罚（`08` 先行下架权仍归平台）。

### 4.3 考试内容（示例方向）

- 馆规五条：托管、分账、举报、退款、先行下架  
- 什么证据系统认、什么不认  
- 律师投票是「支持举报方还是支持商家」而非重新侦查  
- 一题：**律师合议是异步的，不需要同时在线**

## 五、举报 → 系统裁定 → 商家申诉 → 律师评审团（核心流程）

> 以下以 **用户举报商家** 为主轴排逻辑；与 `08` 维权体系衔接。

### 5.1 设计意图

- **先举报，后系统看「举报过不过」**——不是一出事就开庭  
- **举报成立后，商家才有申诉权**——不服可再申请维权  
- **律师评审团异步合议**——对照「举报陈述 + 申诉陈述 + 环境主题」，支持谁  
- **不做同步法庭**——材料先齐，律师错时阅卷投票  

### 5.2 标准流程（一步一步）

```
┌──────────────────────────────────────────────────────────────────┐
│ ① 用户举报                                                        │
│    针对：SKU、订单、店铺行为等                                      │
│    填写：举报类型 + 理由陈述（结构化 + 短文）                        │
│    可选附：订单号、链接（系统自动拉硬日志）                          │
└────────────────────────────┬─────────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────────┐
│ ② 系统裁定：举报过不过（第一道门）                                  │
│    输入：举报文 + 系统硬证据（hash、订单事件、SKU 绑定…）            │
│    输出：                                                          │
│      · 举报不成立 → 结案，通知举报人；恶意举报可扣信誉               │
│      · 举报成立   → 进入③，并通知商家                                │
│    临时措施（可选）：举报成立时先警告 / 限流 / 冻结上架，待后续定案   │
└────────────────────────────┬─────────────────────────────────────┘
                             ▼ （仅「举报成立」时）
┌──────────────────────────────────────────────────────────────────┐
│ ③ 商家收到通知 → 若不服 → 申请维权（申诉）                          │
│    限时提交（如 72h 内），逾期视为接受系统对举报的成立                │
│    填写：申诉陈述——说明为何认为举报不合理                             │
│    系统锁定双方文稿，不可事后篡改（时间戳存证）                      │
└────────────────────────────┬─────────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────────┐
│ ④ 组卷：提交律师评审团（异步）                                     │
│    评审团看到的「一卷」包含三块，且彼此对应同一环境主题：             │
│      A. 【环境主题】被举报对象上下文（SKU 页、订单摘要、店铺条目…）   │
│      B. 【举报方陈述】用户举报时写的内容 + 系统认定的相关硬事实摘要   │
│      C. 【商家申诉陈述】商家不服时写的内容                           │
│    律师的「小小举证」= 阅读上述材料，必要时点开主题内链接核对，       │
│      不要求线下调查，不搞同步辩论                                   │
└────────────────────────────┬─────────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────────┐
│ ⑤ 律师评审团投票（投票窗如 72h，错时）                              │
│    每位注册律师一票：                                              │
│      · 支持举报方（维持对商家的不利认定方向）                       │
│      · 支持商家（认为申诉更有理，应撤销或减轻）                     │
│    可选：短评议（引用馆规条款编号）                                 │
└────────────────────────────┬─────────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────────┐
│ ⑥ 结案                                                            │
│    多数支持举报方 → 按举报成立方向执行（下架、退款、罚信誉等）        │
│    多数支持商家   → 撤销或减轻②的临时措施，举报记为「成立但商家胜诉」│
│    票数不足最低门槛 → 按系统②裁定默认执行（或延长一次投票窗，待定）  │
│    双方系统邮箱通知；卷宗归档（`04`）                               │
└──────────────────────────────────────────────────────────────────┘
```

### 5.3 两阶段分工：系统裁什么、律师裁什么

| 阶段 | 谁 | 裁什么 | 不裁什么 |
|------|-----|--------|----------|
| **② 系统** | 规则引擎 | **举报本身过不过**（形式+硬证据门槛） | 不搞长篇情理辩论 |
| **⑤ 律师团** | 注册律师多数 | **支持举报方还是商家**（情理+馆规+主题上下文） | 不能改订单金额、不能私自划款 |
| **终局执行** | 系统 | 按⑥结果改硬状态（上下架、冻款、信誉） | 人不直接改库 |

**现实对照**：先立案审查（系统）→ 不服上诉（商家申诉）→ 合议庭看双方状纸（律师团）。

### 5.4 「环境主题」是什么

律师不能只看两张吵架截图，必须看到 **被举报的东西长什么样**：

| 举报类型 | 环境主题（卷宗 A 块） |
|----------|------------------------|
| 抄袭 SKU | 该 SKU 页、绑定的 Blueprint 摘要、上架时间 |
| 货不对板 | 订单详情、交付物记录、SKU 承诺描述 |
| 虚假宣传 | 商品文案 vs 沙盒验证结果摘要 |
| 店铺违规 | 店铺公开页、近期成交与评价摘要 |

主题与 **B 举报陈述、C 申诉陈述** 同屏对照，律师才知道在判什么。

### 5.5 与「现实法庭」的差异（刻意简化）

| 现实法庭 | 本作评审团 |
|----------|------------|
| 同步开庭 | **投票窗内随时阅卷投票** |
| 律师当庭辩论 | **双方状纸已锁定** + 可选短评议 |
| 法官一人定案 | **系统裁举报过不过 + 律师团裁支持谁** |
| 举证复杂 | **小小举证** = 读卷宗 + 点主题链接 |
| 严肃仿真 | **馆规剧场**——有流程感，不折磨人 |

### 5.6 谁说了算？

| 层级 | 权力 |
|------|------|
| **系统②** | 举报过不过；不过则商家无申诉必要 |
| **商家③** | 不服才可进入律师团；服则按②结案 |
| **律师团⑤** | **支持谁**的多数决 → 决定终局方向 |
| **系统⑥** | 执行终局；选项来自馆规预设表，非律师任意填数 |
| **平台** | 违法/重大风险 **一票否决**（`08`） |

律师团是 **看双方状纸与主题的陪审团**，不是第二个数据库管理员。

### 5.7 防滥投与环境保护

| 风险 | 对策 |
|------|------|
| 律师刷票换币 | 单案一票；奖励声望非货币为主；日投票上限 |
| 律师串通 | 随机抽案参与（后期）；异常一致票型审计 |
| 无人投票 | 期满按系统初判**自动结案**（律师是增强正当性，非阻塞） |
| 拖延正义 | 投票窗有上限；临时措施（冻结）已有 |
| 律师当武器骚扰 | 恶意不认同率高的吊销资质 |

## 六、与合规文档（08）的关系

| `08` 概念 | 玩家律师扮演 |
|-----------|--------------|
| L1 馆规自动化 | **系统裁「举报过不过」** |
| L1.5 玩家律师团 | **支持举报方 vs 商家** 多数决 |
| L2 合作律师 | **复核队列**（极端案、平台否决上诉） |
| L3 外部司法 | 平台外仍可走现实法律；游戏内合议不替代 |
| 先行下架 | 举报后仍可先冻，合议确认后维持或恢复 |
| 版权侵权 | 卷宗含 hash 比对结果，律师投认同与否 |

玩家律师 **不替代** 平台法务与真实律师；是 **馆内正当性 + 参与感**。

## 七、其他职业是否也要「简单考」？

| 职业 | 建议 |
|------|------|
| 律师 | **要**——影响他人权益 |
| 行者 / 服务员 | **轻量执照**（已有方向 `01`） |
| 商家 | **开店考**——托管与库存常识，同样偏简单 |
| 方案方 B₁ | **模板工作坊通关**（`07` 沙盒即考） |
| 食客 | 无考 |

统一原则：**考的是「读规则意愿」**，不是为难人。

## 八、MVP 可验证什么

1. 馆规考 10～20 题，通过后得「注册律师」  
2. 一种案件：**用户举报 SKU / 订单** → 系统裁举报过不过 → 商家申诉  
3. 评审团卷宗：环境主题 + 举报陈述 + 申诉陈述  
4. 律师投「支持举报方 / 支持商家」+ 72h 投票窗  
5. 票数不足 → 按系统②裁定默认执行（待定规则）  
6. 双方邮箱收结案通知；卷宗可查阅（脱敏）  
7. 问玩家：是否感觉「有规矩」又不像上班？

## 九、举一反三：更多案型范本（现实 / 线上）

> 以下案型共用 **§5.2 六步骨架**，只换当事人、环境主题与终局处置表。  
> 格式统一，便于往文档里继续加料。

### 9.0 通用模板（复制用）

```text
【案型名称】
  现实类比 / 线上类比：
  举报方 → 被举报方：

  ① 举报：举报方陈述什么
  ② 系统裁「举报过不过」：硬证据看什么
  ③ 申诉：被举报方不服时陈述什么（限时）
  ④ 环境主题（卷宗 A）：律师对照看的上下文
  ⑤ 律师团：支持举报方 / 支持被举报方
  ⑥ 终局（系统预设）：胜诉方对应处置

  新奇点：（可选）
```

---

### 案型 1：商品货不对板（你已举过的主线）

| 项 | 内容 |
|----|------|
| **类比** | 网购退货纠纷 / 外卖与图文不符 |
| **举报方 → 被举报方** | 买家 C → 商家 B₂ |
| **① 举报** | 「买到的委托包次数不对 / 描述与体验不符」 |
| **② 系统** | 查 `library` 权益、SKU 描述、Blueprint 沙盒摘要；订单 `ledger` |
| **③ 申诉** | 商家：「描述准确，是买家未按说明使用」 |
| **④ 环境主题** | SKU 页 + 购买记录 + 已发放 deliverable 快照 |
| **⑤ 律师团** | 支持买家 / 支持商家 |
| **⑥ 终局** | 买家胜：退款或补发次数；商家胜：维持交易，买家信誉若恶意举报则扣 |

---

### 案型 2：Blueprint 抄袭 / 盗卖方案

| 项 | 内容 |
|----|------|
| **类比** | 著作权侵权投诉 / App Store 抄袭下架 |
| **举报方 → 被举报方** | 方案方 B₁ → 产品方 B₂（或另一 B₁） |
| **① 举报** | 「对方 SKU 绑定的方案与我授权范围不符 / 结构高度相似」 |
| **② 系统** | `blueprint_hash` 比对、授权记录、上架时间先后 |
| **③ 申诉** | 被举报方：「已获授权 / 独立编排 / 仅包装不同」 |
| **④ 环境主题** | 双方 Blueprint 摘要（脱敏 nodes）+ 授权合约 + 两 SKU 对照 |
| **⑤ 律师团** | 支持举报方 / 支持被举报方 |
| **⑥ 终局** | 举报方胜：下架 SKU、冻结未结款、恢复授权链；对方胜：维持上架 |

---

### 案型 3：服务单「接了不干活」

| 项 | 内容 |
|----|------|
| **类比** | 家政/咨询投诉 /  freelancing 里程碑纠纷 |
| **举报方 → 被举报方** | 发单方 A → 服务员 B |
| **① 举报** | 「超时无进展 / 交付与约定不符」 |
| **② 系统** | 服务单状态机、`order_events`、里程碑节点是否触发 |
| **③ 申诉** | 服务员：「已按节点完成，发单方恶意拖验收」 |
| **④ 环境主题** | 服务单详情 + 往来信箱信串摘要 + 约定里程碑列表 |
| **⑤ 律师团** | 支持发单方 / 支持服务员 |
| **⑥ 终局** | 发单方胜：退款、服务员扣信誉；服务员胜：强制验收放款 |

---

### 案型 4：地图粉笔字 / 痕迹骚扰

| 项 | 内容 |
|----|------|
| **类比** | 公共场所涂鸦 / 平台留言辱骂 |
| **举报方 → 被举报方** | 到访者 / 地点管理者 → 留痕者 |
| **① 举报** | 「辱骂、广告、剧透、色情」类粉笔字 |
| **② 系统** | 痕迹文本敏感词、同地重复率、留痕者历史封禁 |
| **③ 申诉** | 留痕者：「属于角色扮演 / 未违规」 |
| **④ 环境主题** | **地点页** + 该痕迹全文 + 同地点前后 10 条痕迹上下文 |
| **⑤ 律师团** | 支持举报方 / 支持留痕者 |
| **⑥ 终局** | 举报方胜：删痕、禁言留痕 N 天；留痕者胜：恢复显示 |

*新奇点：地点本身就是「环境主题」，律师像判「这条街该不该留这句话」。*

---

### 案型 5：往来信箱骚扰

| 项 | 内容 |
|----|------|
| **类比** | 邮件骚扰 / 私信辱骂 |
| **举报方 → 被举报方** | 收信人 → 发信人 |
| **① 举报** | 「骚扰、诈骗话术、频次异常」 |
| **② 系统** | 信串 `thread_id`、频次、是否含站外交易诱导 |
| **③ 申诉** | 发信人：「正常议价 / 误会」 |
| **④ 环境主题** | 脱敏信串（隐藏第三方隐私）+ 是否关联进行中订单 |
| **⑤ 律师团** | 支持收信人 / 支持发信人 |
| **⑥ 终局** | 收信人胜：禁发信、订单若存在则冻结；发信人胜：解除限制 |

*与 `04` 异步通讯直接挂钩。*

---

### 案型 6：悬赏完成纠纷（双向）

| 项 | 内容 |
|----|------|
| **类比** | 众包验收扯皮 /  freelancer 拒付尾款 |
| **方向 A** | 发布者举报接单者：「假完成」 |
| **方向 B** | 接单者举报发布者：「恶意拒验收」 |
| **② 系统** | 客观子任务校验结果 + 提交物 hash + 时间戳 |
| **④ 环境主题** | 悬赏原文 + 子任务清单 + 完成提交记录 |
| **⑤ 律师团** | 支持举报方 / 支持被举报方（谁举报支持谁的对立面） |
| **⑥ 终局** | 托管款按胜诉方规则释放或退回 |

*同一案型框架，当事人可互换——系统②先认「举报是否立案」。*

---

### 案型 7：恶意评价 / 刷好评

| 项 | 内容 |
|----|------|
| **类比** | 电商差评纠纷 / 水军评价 |
| **举报方 → 被举报方** | 商家 B₂ → 评价者 C（或反向：买家举报商家刷评） |
| **① 举报** | 「未购买却评 / 同行恶意一星」 |
| **② 系统** | `owns(sku)`、游玩时长、评价时间与购买时间差 |
| **③ 申诉** | 评价者：「确实购买且体验差」 |
| **④ 环境主题** | 评价全文 + 购买/游玩记录 + SKU 页 |
| **⑤ 律师团** | 支持商家 / 支持评价者 |
| **⑥ 终局** | 商家胜：隐藏或删除评价、恢复评分；评价者胜：维持评价 |

---

### 案型 8：版税 / 分账异议（偏硬，少情理）

| 项 | 内容 |
|----|------|
| **类比** | 供应商对账单异议 / 音乐版税结算 |
| **举报方 → 被举报方** | B₁ 方案方 → B₂ 产品方（或系统账单） |
| **① 举报** | 「某 SKU 成交未按 royalty 分账」 |
| **② 系统** | `ledger_entries` 几乎可一锤定音；举报过不过偏客观 |
| **③ 申诉** | B₂：「授权已过期 / 该笔为退款冲正」 |
| **④ 环境主题** | 分账流水 + 授权有效期 + 对应订单列表 |
| **⑤ 律师团** | 多数案 **系统②已足够**；律师主要判「申诉理由是否成立」 |
| **⑥ 终局** | 补分账 / 维持原账 |

*新奇点：律师团更像「看账单的陪审团」——可引出第二职业 **审计员** 专精此类。*

---

### 案型 9：情报单「剧透 / 货不对板」（线上特色）

| 项 | 内容 |
|----|------|
| **类比** | 付费咨询内容与承诺不符 |
| **举报方 → 被举报方** | 买家 C → 情报贩子 B |
| **① 举报** | 「买的是未解锁条目，却收到剧透全文」 |
| **② 系统** | 交付物是否为预定义 `intel_id` vs 自由文本 |
| **③ 申诉** | 卖方：「条目定义含该信息」 |
| **④ 环境主题** | 情报单承诺摘要 + 实际交付条目 + 买家已解锁进度 |
| **⑤ 律师团** | 支持买家 / 支持卖方 |
| **⑥ 终局** | 退款、卖方禁售情报类 N 天 |

---

### 案型 10：口味标签欺诈（较新奇）

| 项 | 内容 |
|----|------|
| **类比** | 餐厅标「清真」却违规 / 游戏标签欺诈 |
| **举报方 → 被举报方** | 食客 C → 厨师或 SKU 发布者 |
| **① 举报** | 「标的是清淡叙事，实际是恐怖跳 scare」 |
| **② 系统** | SKU/订单「口味标签」vs Blueprint 实际节点 tone 检测结果 |
| **③ 申诉** | 发布者：「口味主观 / 标签含多义」 |
| **④ 环境主题** | 点菜单口味勾选 + SKU 标签 + 沙盒 tone 扫描摘要 |
| **⑤ 律师团** | 支持食客 / 支持发布者 |
| **⑥ 终局** | 部分退款、改标签、扣信誉 |

*与 `02` 口味谱挂钩——律师判的是「吃起来像不像点的菜」。*

---

### 案型 11：试玩片段与全版不符（数字商品）

| 项 | 内容 |
|----|------|
| **类比** | 宣传片与游戏不符 / 试吃与正餐两样 |
| **举报方 → 被举报方** | 买家 C → B₂ 发行方 |
| **① 举报** | 「试玩章精彩，全版缩水」 |
| **② 系统** | 试玩 Blueprint 与全版 `nodes` 完成度对比、时长对比 |
| **③ 申诉** | 发行方：「试玩本就是节选，描述已写明」 |
| **④ 环境主题** | 商店页描述 + 试玩记录 + 全版进度条 |
| **⑤ 律师团** | 支持买家 / 支持发行方 |
| **⑥ 终局** | 触发 `01` Steam 式退款窗口内则退款；否则仅改描述 |

### 案型 12：评审团评议本身被举报（元案件，新奇）

| 项 | 内容 |
|----|------|
| **类比** | 法官回避 / 陪审员偏见投诉 |
| **举报方 → 被举报方** | 当事人 → 某律师的评议 |
| **① 举报** | 「评议含人身攻击 / 明显未阅卷」 |
| **② 系统** | 评议字数、阅卷停留时间（若记录）、与卷宗关键词重合度 |
| **③ 申诉** | 律师：「专业措辞，非人身攻击」 |
| **④ 环境主题** | 被诉评议全文 + 原案卷宗链接 |
| **⑤ 律师团** | **另一批**律师投（回避原案参与者） |
| **⑥ 终局** | 吊销律师资格 / 驳回举报 |

*防律师权力滥用；规则要单独写，MVP 可不做。*

## 十一、小结

| 问题 | 答案 |
|------|------|
| 职业谁扮演？ | **玩家**；系统给资质与硬边界 |
| 严肃现实吗？ | **不**；但有馆规氛围与卷宗仪式感 |
| 律师怎么当？ | **简单资格考** → 注册律师 |
| 完整流程？ | 用户举报 → **系统裁举报过不过** → 商家不服可申诉 → **律师团看双方状纸+主题** → 支持谁 → 结案 |
| 同步法庭？ | **不做** |
| 律师做什么？ | **小小举证**=读卷宗；投票支持举报方或商家 |
| 律师能私自改钱吗？ | **不能**；系统按馆规预设执行终局 |

> 用户先举报，系统先看状纸过不过；商家不服再写申诉。  
> 两状纸与那件货搁在同一主题下，送进评审团。律师睡醒、阅卷、选边站——馆规便落地。
