## 一、核心想法（一句话）

玩家持有订单（自点的「我要」单，或自愿从悬赏/公告栏接的单）后，可以**把任务拆成若干子任务**，以**自定义报酬**发布到公共悬赏板；其他玩家按意愿接单、完成后，发布者的原任务才算整体完成并可提交。

> **与点菜式成长的立场**（详见 `02`）：**没有主线**。系统单挂**悬赏栏/公告栏**自取；**订阅前零推送**。**系统邮箱**被动接收待领取奖励、成就庆祝与重要公告（**手动点领取**入包）。**成就门槛**触发庆祝信 + 可选拓展提示，不派活。**文本背包默认无上限**。  
> **与地图探索**（详见 `03`）：地点基于世界百科 ID；**经过即打卡**、链接变色；**异步痕迹**挂地点、全局可见；逻辑上**一个大世界**，多机为无状态 API + 共享库，不做玩家选服。  
> **与异步通讯**（详见 `04`）：默认**往来信箱**而非实时聊天；全球错时友好；商单沟通走信串；硬状态服务器算，软沟通信箱传。  
> **与界面壳层**（详见 `05`）：**无固定首页**，壳层挂件随车走；状态**按需/条件轮询**，标签页不可见时暂停。

## 二、玩家流程

```
系统 ──派发──► 玩家 A（接任务）
                    │
                    ▼ 拆分
              子任务 1、2、3…
                    │
                    ▼ 设定报酬 + 发布
              公共悬赏板 / 任务市场
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
     玩家 B       玩家 C       玩家 D
    （接单）      （接单）      （不接）
        │           │
        ▼           ▼
      完成         完成
        │           │
        └─────┬─────┘
              ▼
    所有子任务均已完成
              │
              ▼
    玩家 A 的原任务视为完成 → 向系统提交
```

### 参与角色

| 角色 | 做什么 |
|------|--------|
| **任务持有者**（发布者） | 从系统接到任务 → 拆分子任务 → 设定报酬 → 发布 → 等全部完成 → 提交 |
| **接单者** | 浏览悬赏 → 看报酬是否值得 → 接单 → 执行 → 交付 |
| **系统** | 派发任务、验收子任务、结算报酬、判定原任务是否可提交 |

### 关键规则（来自想法 + 建议补全）

| 规则 | 说明 |
|------|------|
| 报酬自定 | 子任务报酬由**发布者**设定，接单者凭「够不够诱人」自行决定 |
| 等级不限 | 接单者等级可高可低，不设硬性门槛（或仅设软门槛，见下文） |
| 自愿接单 | 无强制匹配，市场自发平衡 |
| 全部完成才过关 | 发布者名下**所有已发布的子任务**都完成后，原任务才可提交 |
| 心情驱动 | 核心动机是报酬与风险/时间的权衡，而非等级压制 |

## 三、外卖式派单：现实对照与体系融合

### 3.1 现实外卖在做什么

以常见外卖平台（美团、饿了么等）为例，核心链路是：

```
商家出餐 ──► 平台生成订单 ──► 骑手抢单/被派单
                │
                ▼
           骑手取餐 → 配送 → 送达客户
                │
                ▼
           平台校验完成 ──► 结算报酬（给骑手、抽成、给商家）
```

| 现实角色 | 做什么 | 钱从哪来 |
|----------|--------|----------|
| **平台** | 生成订单、匹配骑手、托管资金、判定完成、防作弊 | 抽成 + 规则 |
| **商家** | 提供货物（餐品），发起配送需求 | 销售收入 |
| **骑手** | 抢单/接单 → 取货 → 送货 → 点完成 | 配送费（平台结算） |
| **客户** | 收餐、确认（或超时自动确认） | 已预付 |

关键特征：**报酬不由客户直接塞给骑手**，而是**平台托管 → 完成后再派发**，减少赖账和纠纷。

### 3.2 映射到 MiraWorld

| 外卖现实 | 游戏内对应 | 说明 |
|----------|------------|------|
| 平台 | **系统** | 规则、匹配、托管、结算、反作弊 |
| 商家 / 出餐 | **任务来源** | 系统任务，或玩家拆分后发布的子任务 |
| 骑手 | **接单者（行者 / 信使）** | 浏览订单池、抢单、执行、交付 |
| 客户 / 送达点 | **任务目标** | NPC、地点、物品交付点、剧情节点 |
| 配送费 | **报酬** | 系统补贴 + 发布者悬赏（可组合） |

### 3.3 两种可并存的派单模式

原先想法偏「**玩家当老板、雇人干活**」（悬赏板）。外卖模型偏「**系统当调度、行者抢单**」。建议**并存**，用任务类型区分：

#### 模式 A：玩家悬赏（老板外包）

```
系统任务 → 玩家 A 持有 → 拆单 + 自定报酬 → 悬赏板
→ 其他玩家自愿接单 → 完成后 A 的原任务可提交
```

- 报酬：**发布者出**（预扣托管）
- 动机：玩家策略、省钱/省时间
- 像：商家自己加价找跑腿

#### 模式 B：系统派单（外卖抢单）

```
系统生成「跑腿单 / 信使单」→ 进入公共订单池
→ 在线/符合条件的玩家抢单（或系统推送候选）
→ 取件 → 送达 → 系统验收 → 系统发报酬
```

- 报酬：**系统出**（或系统底薪 + 发布者小费）
- 动机：纯打工、刷日常、练级
- 像：平台派单给骑手，完成即结账

#### 模式 C：混合（推荐用于「玩家拆单」）

玩家拆出的子任务，**进入系统订单池**统一展示（而不只是好友可见），由系统：

1. **托管**发布者预扣的报酬  
2. **展示**给所有符合条件的行者（像外卖列表）  
3. **验收**完成后**自动结算**给接单者  
4. **回写**进度给发布者的原任务  

这样「玩家悬赏」在体验上接近外卖抢单，但资金来自发布者；「系统派单」则资金来自系统，两者 UI 可以共用**同一个订单池界面**，用标签区分「悬赏 / 系统」。

```
                    ┌─────────────────┐
                    │   公共订单池     │
                    │ （统一列表 UI）  │
                    └────────┬────────┘
              ┌──────────────┼──────────────┐
              ▼              ▼              ▼
         系统派单        玩家悬赏        公会委托
        （系统付）      （发布者付）     （公会池付）
              │              │              │
              └──────────────┴──────────────┘
                             ▼
                    行者抢单 → 执行 → 交付
                             ▼
                    系统验收 → 自动结算报酬
```

### 3.4 外卖模型值得借鉴的机制

| 外卖做法 | 游戏内落地 |
|----------|------------|
| 抢单 / 派单二选一 | 默认抢单（玩家有掌控感）；高优先级单可系统指派给高信誉行者 |
| 订单超时自动取消 | 接单后 N 分钟未取件/未送达 → 回池或判失败 |
| 路线 / 距离显示 | 文字游戏里用「地点距离、危险度、预计耗时」代替地图 |
| 客户确认收货 | 客观任务系统自动确认；主观任务短申诉期后自动过 |
| 骑手评分 | 接单者信誉分，影响抢单优先级 |
| 平台垫付纠纷 | 报酬已托管，**不经过发布者手**再点同意 |

### 3.5 玩家商单：A ↔ 系统 ↔ B（核心三角）

> **此玩家非彼玩家**：下文 **玩家 A** 指**发单 / 需求方**（我要东西或我要服务）；**玩家 B** 指**接单 / 供给方**（我来卖、我来干、我来送）。同一个人在不同订单里可以有时是 A、有时是 B。

商单往往**发源于玩家自身**：玩家 A 希望平台帮自己办成一件事 → **系统接单** → 按订单类型派给具备相应**注册身份**的其他玩家 → 完成后回到玩家 A。

```
                    ┌──────────────┐
                    │    系统      │
                    │ （平台调度）  │
                    │ 接单·拆单·托管│
                    │ 匹配·验收·结算│
                    └──────┬───────┘
                           │
           ┌───────────────┼───────────────┐
           │                               │
           ▼                               ▼
    ┌─────────────┐                 ┌─────────────┐
    │  玩家 A     │                 │  玩家 B     │
    │ （需求方）   │                 │ （供给方）   │
    │ 我要…       │                 │ 身份可多选： │
    │ 预付/托管   │                 │ 商家/服务员/ │
    └─────────────┘                 │ 骑手…       │
           │                         └─────────────┘
           │    最终交付 / 服务完成          │
           └──────────────◄─────────────────┘
```

**系统居中**：不偏向 A 或 B，负责规则、资金托管、拆分子环节、防作弊。A 与 B **不直接私下成交**，一律经系统过账（见第四章）。

#### 3.5.1 两类商单

| 类型 | 玩家 A 要什么 | 玩家 B 是谁 | 履约方式 |
|------|----------------|-------------|----------|
| **服务单** | 请人办事（调查、陪护、远程代录、修理…） | **注册服务员** | **上门**（到指定地点）或 **远程**（文字交互/异步完成） |
| **商品单** | 买实物（如点 5 份外卖） | **商家** 备货 + **骑手** 配送（可两个 B） | 商家备料打包 → 骑手取货 → 送到 A |

同一张商品单里，**商家 B₁** 与 **骑手 B₂** 是不同环节的两个玩家（也可合并设计为 NPC 商家 + 玩家骑手，MVP 可先简化）。

#### 3.5.2 服务单流程

```
玩家 A：在平台发布「我需要 XXX 服务」+ 报酬（系统托管）
    │
    ▼
系统：审核描述 → 生成服务单 → 推送给符合条件的注册服务员
    │
    ▼
玩家 B（服务员）：抢单 / 被指派 → 上门 或 远程执行
    │
    ▼
系统：验收（客观节点 / 服务时长 / A 确认或超时自动确认）
    │
    ▼
结算：B 得服务费，系统抽成，A 的需求标记完成
```

**注册服务员身份**（需单独解锁，类似骑手执照）：

- 可设**服务类目**（仅接调查类、仅接护送类…）
- **上门**：需到达游戏内地点标记  
- **远程**：纯文字会话、提交成果物、异步留言单  

#### 3.5.3 商品单流程（以「点 5 份外卖」为例）

```
玩家 A：下单「5 份 XX 餐」+ 地址 + 总价（系统托管）
    │
    ▼
系统：拆单 ──┬──► 子单① 备餐（给商家）
              └──► 子单② 配送（给骑手，依赖①完成）
    │
    ▼
玩家 B₁（商家）：接单 → 备齐 5 份食材 → 烹饪/打包为「商品」库存扣减
    │
    ▼
系统：商家点「出餐完成」→ 商品进入「待取件」状态
    │
    ▼
玩家 B₂（骑手）：抢配送单 → 到商家取货 → 送达 A 指定地点
    │
    ▼
系统：A 收餐确认（或超时自动确认）→ 货款给 B₁，配送费给 B₂，平台抽成
```

要点：

- **商家**负责「把需求变成可交付的商品」（备料、打包、扣库存）。  
- **骑手**负责「位移」，不负责做菜。  
- **系统**把一张用户订单拆成**备餐子单 + 配送子单**，可先后依赖（骑手单在商家出餐后才可抢）。

#### 3.5.4 与「系统任务 / 玩家拆悬赏」的关系

| 来源 | 谁发起 | 系统角色 |
|------|--------|----------|
| 系统任务 | 系统 | 派给玩家 A；A 可选择再拆悬赏 |
| **玩家商单** | **玩家 A** | **平台代接单**，再匹配 B（商家/服务员/骑手） |
| 玩家悬赏 | 玩家 A（持系统任务者） | 托管报酬，进订单池 |

可以看成三层：

```
玩家 A 的商单（顶层需求）
    → 系统接单并可能拆成多个环节子单
        → 各类注册身份的玩家 B 接子单
            → 全部环节完成 → A 的商单完成
```

原先「拆成多个子任务发布」的想法，在商单模型里变成：**系统帮 A 拆**（商品单自动拆商家+骑手），或 **A 在发布时声明**（服务单可拆为「远程咨询 + 上门收尾」等，高级功能可后置）。

#### 3.5.5 注册身份一览（玩家 B 侧）

一个账号可拥有多种**平台注册身份**（分模块解锁）：

| 身份 | 接什么单 | 履约 |
|------|----------|------|
| **注册服务员** | 服务单 | 上门 / 远程 |
| **注册商家** | 商品单的备餐/备货子单 | 消耗库存、打包 |
| **注册骑手** | 商品单的配送子单 | 取货 → 送达 A |
| **行者（通用）** | 系统派单、简单跑腿 | 与外卖模型一致 |

身份分离的好处：规则清晰、防一个人刷完「自卖自买自送」整条链（需系统限制同账号不能同时当 A 和 B₁/B₂，见第四章）。

#### 3.5.6 资金拆分（商品单示例）

玩家 A 支付 **100**（托管）：

| 去向 | 金额（示例） |
|------|----------------|
| 商家 B₁（货款） | 70 |
| 骑手 B₂（配送费） | 20 |
| 平台抽成 | 10 |

具体比例可由**商家定价 + 系统运费规则**决定；A 下单时看到**总价明细**，避免纠纷。

#### 3.5.7 世界观包装（MiraWorld）

| 现实概念 | 世界内称呼 |
|----------|------------|
| 平台下单 | 在「潮灯驿站」挂委托 / 点单 |
| 商家 | 港口食肆、镜湖驿茶寮、商会铺面（玩家开店） |
| 服务员 | 拾遗院外勤、商会清道夫、信使 |
| 骑手 | 潮灯信使、渡口的脚夫 |
| 送达 | 「灯号确认」——目的地灯亮即视为签收 |

#### 3.5.8 待细化（商单专用）

## 四、防恶意攻击机制（安全设计）

> 目标：让体系像外卖平台一样**可运营**，而不是被小号、脚本、勾结玩家刷崩经济或恶心他人。

### 4.1 威胁模型：谁会攻击、怎么攻击

| 攻击类型 | 具体行为 | 后果 |
|----------|----------|------|
| **刷资源** | 小号互发任务、互接互完成，转移货币 | 经济通胀、公平崩坏 |
| **恶意挂单** | 虚假描述、极低报酬骗劳动力 | 新手上当、口碑差 |
| **占单不放** | 抢单后挂机，阻止他人完成 | 发布者任务卡死 |
| **脚本抢单** | 机器人毫秒抢光高报酬单 | 真人抢不到 |
| **代打剧透** | 大号代做主线外包单 | 叙事体验被破坏 |
| **骚扰 / 诈骗** | 私聊诱导线下交易、冒充系统 | 玩家流失、信任危机 |
| **重复结算** | 同一进度多次提交领奖 | duplicate 漏洞 |
| **负价 / 溢出** | 异常报酬数值 | 数据库或经济异常 |
| **自卖自送自买** | 同一玩家当 A 又当商家+骑手 | 虚假交易刷信誉/货币 |

### 4.2 资金层：托管与单向流动（学外卖）

```
发布者发起子任务
    → 系统立刻锁定（预扣）报酬 + 手续费
    → 接单者不可见「口头承诺」，只见「已托管 X」
    → 验收通过 → 系统划给接单者（扣手续费后）
    → 失败/取消 → 按规则退回发布者（扣违约金若有）
```

**原则：玩家之间不直接转账完成任务。** 所有报酬经系统过账，留审计日志。

防刷补充：

- **关联账号检测**：同设备 / 同 IP / 近期互转过账的账号，**禁止互接**或收益衰减 90%
- **冷却**：同一对 (发布者, 接单者) 24h 内最多完成 N 单
- **新号限制**：注册 72h 内不可发布悬赏，只可接系统派单且报酬上限低
- **异常流量**：单日接单收入超阈值 → 人工或延迟审核
- **商单闭环限制**：同一账号（及关联号）**不可在同一笔商单中**同时担任 A 与 B（商家/骑手/服务员）；三环节至少两个不同真人账号（商家+骑手不能是同一人兼两职完成整单，除非 MVP 用 NPC 商家）

### 4.3 抢单层：防占单、防脚本

| 机制 | 说明 |
|------|------|
| **同时持单上限** | 行者最多 1～3 个进行中订单（随信誉提升） |
| **接单押金（可选）** | 接高报酬单需冻结小额押金，完成退还；恶意放弃扣除 |
| **抢单冷却** | 放弃/超时后 5～15 分钟内不可再抢同类单 |
| **随机延迟入池** | 新单上架后 0～3 秒随机才可抢，削弱脚本优势 |
| **行为校验** | 关键步骤需在游戏内真实操作（到达地点、提交物品、对话选项），非纯 API 秒点 |
| **人机验证（轻量）** | 高频抢单触发简单验证（网页可做点击/滑块） |

### 4.4 验收层：只信系统，不信口头

| 任务类型 | 验收 | 防作弊 |
|----------|------|--------|
| 收集 / 送达 | 背包数量 + 地点标记 | 物品来源日志，拒绝「凭空出现」 |
| 对话 / 调查 | 选项树关键节点命中 | 必须按顺序触发，不可跳关 |
| 限时跑腿 | 时间戳 + 路径节点 | 异常短完成时间标记复审 |

**不接受**发布者手动点「他做完了」作为唯一依据（可被要挟或勾结）。发布者仅有**申诉**权，不能单方面克扣已托管报酬。

### 4.5 权限与任务分层（防代打、防滥用）

| 任务标签 | 进订单池 | 报酬来源 | 备注 |
|----------|----------|----------|------|
| `system_daily` | 是 | 系统 | 外卖主模式 |
| `player_bounty` | 是 | 发布者托管 | 玩家拆单 |
| `main_story` | **否** | — | 不可外包 |
| `main_story_optional` | 否或仅公会 | 系统 | 若允许协作需单独设计 |
| `guild` | 公会内池 | 公会金库 | 防全服刷 |

### 4.6 信誉与惩罚（学骑手评分）

双向评分：

- **接单者**：完成率、准时率、被申诉率 → 影响抢单优先级、持单上限、可否接高价单  
- **发布者**：描述准确度、恶意撤单率 → 影响发布额度、手续费倍率  

惩罚阶梯：

1. 警告 → 限制抢单 24h  
2. 扣信誉 → 降低收益  
3. 封禁悬赏/抢单功能  
4. 封号（极端刷资源）  

### 4.7 烂尾与「卡死」兜底（学订单超时）

| 情况 | 系统行为 |
|------|----------|
| 无人抢单 | 超时后提醒发布者加价 或 收回自行完成 |
| 抢单后不动 | 取件超时 → 自动回池，扣接单者信誉/押金 |
| 进行中太慢 | 送达超时 → 失败回池或转给后备行者 |
| 发布者下线 | 不影响；报酬已托管，系统照常结算 |

### 4.8 审计与运营后台（后续）

即使 MVP 不做 UI，**数据库层建议预留**：

- 订单状态机日志（created → claimed → in_progress → delivered → settled）  
- 每笔资金变动关联 `order_id`  
- 便于日后查「谁刷的」「哪单卡了」  

与现有账号系统衔接：注册登录已具备，后续可加「行者资格」开关（完成新手教程后解锁抢单）。

### 4.9 融合后的推荐默认规则（小结）

1. **双模式**：系统派单（平台付）+ 玩家悬赏（托管付），共用订单池 UI  
2. **资金不经人手**：预扣 → 验收 → 自动结算  
3. **关联号互刷**：硬限制或强衰减  
4. **叙事/沉浸单不可外包**（无「主线」概念），跑腿类可抢单  
5. **持单上限 + 超时回池**，防占单  
6. **信誉双向**，影响权限与收益  
7. **验收只认系统**，发布者仅申诉

## 五、设计意图与优点

### 1. 社交协作，而非单机刷任务

- 把「一个人做完一整条任务链」变成「组织 + 外包」。
- 适合 MiraWorld 这种**文字探索 / 叙事世界**：任务可以是调查、送信、搜集线索、谈判等，天然适合分工。

### 2. 玩家经济与市场行为

- 报酬自定 → 形成**任务市场价格**：难活贵、闲人接便宜活。
- 可衍生：情报贩子、任务中介、公会包单等专业角色。

### 3. 策略深度

- 发布者要在「总报酬成本」和「完成速度」之间权衡：拆得越细，协调成本越高，但可能更快。
- 接单者要在「报酬 / 难度 / Reputation」之间权衡。

### 4. 与网页形态契合

- 异步：接单、完成、交付都不需要同时在线。
- 列表 + 详情页即可支撑悬赏板 UI，无需复杂实时战斗。

### 5. 可扩展叙事

- 子任务描述可以是世界观内的「委托函」「悬赏令」，强化沉浸感。

## 六、风险与缺点

| 问题 | 说明 |
|------|------|
| **搭便车 / 甩手掌柜** | 发布者只拆单、不干活，若报酬全外包，可能削弱个人体验 |
| **恶意低价** | 极低的报酬刷屏，或诱导新手做苦力 |
| **烂尾单** | 子任务无人接 → 原任务永久卡住 |
| **纠纷** | 「做完了但发布者不认可」需验收标准 |
| **洗钱 / 刷资源** | 若报酬是游戏货币，需防小号互刷 |
| **协调成本** | 拆太碎，发布者要盯多个进度，反而更累 |
| **剧透 / 跳过体验** | 主线剧情被高等级玩家代打，叙事节奏被打断 |

## 七、建议补充的设计点

### 7.1 任务来源与展示（无主线）

**没有主线任务树。** 订单来源分三类，均进同一订单池 UI，用标签区分：

| 来源 | 展示位置 | 是否推送 | 是否可拆分子任务 |
|------|----------|----------|------------------|
| **玩家自点**（「我要」） | 订单池 / 可选公开 | 否（除非他人订阅了你） | 是 |
| **系统公告单**（偏新手、偏简单） | **悬赏栏 / 公告栏** | **否**；挂栏自取 | 视单类型标记 |
| **玩家悬赏**（持单者拆单） | 悬赏栏 | 否 | 子任务不可再拆（见 §7.5） |

系统单 ≠ 主线：不接、不锁功能、不弹窗催。玩家叙事类成长来自**自己点的单**或**自愿接的栏上单**，不是「当前章节必做」。

**拆分权限**（替代原「主线不可外包」）：

| 类型 | 是否可外包 | 说明 |
|------|------------|------|
| 叙事 / 沉浸体验单（玩家或创作者标记） | 否 / 仅部分 | 保护体验，防代打剧透 |
| 跑腿 / 收集 / 日常类 | 是 | 适合市场 |
| 公会 / 世界事件 | 是（公会内或全服） | 放大协作感 |

### 7.2 报酬与托管

- 发布时**锁定报酬**（预扣货币或道具），避免完成后赖账。
- 子任务完成 → **系统自动发放**给接单者，减少纠纷。
- 无人接单超过 N 小时：提醒发布者加价、合并子任务或收回自行完成。

### 7.3 验收机制

| 子任务类型 | 验收方式 |
|------------|----------|
| 客观目标（收集 3 件 X） | 系统自动校验背包 / 计数 |
| 主观目标（与 NPC 谈判） | 提交文本摘要 + 可选截图/关键词，或系统根据选项树校验 |
| 高风险 | 双人确认或短申诉期 |

### 7.4 信誉与防刷

- **接单者信誉**：完成率、好评、爽约记录。
- **发布者信誉**：按时付款、描述是否准确。
- 同 IP / 同设备 / 互相关联账号：**限制互刷**或降低收益。
- 每日外包收益上限（可随等级放开）。

### 7.5 拆分约束（避免无限套娃）

- 系统任务最多拆 **1～2 层**（系统任务 → 子任务，子任务不可再拆）。
- 或：只有「系统标记为可拆分」的任务才能进悬赏板。
- 单次发布子任务数量上限（如 3～5 个）。

### 7.6 等级「随意」的细化

想法是等级不限，但可以做成**软限制**而非硬门槛：

- 不禁止低等级接高难度单，但任务描述里标「推荐等级 / 危险度」。
- 失败不扣报酬押金，但可能扣信誉或浪费冷却时间。
- 高等级接低级单：报酬衰减，避免大号扫货垄断。

### 7.7 烂尾与超时

- 子任务可设**截止时间**；超时自动回到悬赏板或失败。
- 发布者可选：**保底自完成**（超时后自己接回）或 **自动退款给发布者**（扣除少量手续费）。

### 7.8 UI / 信息架构（网页）

建议页面：

1. **我的任务** — 系统派的、进行中、可拆分
2. **悬赏板** — 筛选：报酬、类型、危险度、剩余时间
3. **我接的单** — 进行中 / 已完成
4. **我发的单** — 进度条：3/5 子任务已完成

---

### 7.9 订单池页面（外卖式 UI 补充）

在原有页面基础上，公共列表建议展示：

| 字段 | 说明 |
|------|------|
| 订单类型 | 系统派单 / 玩家悬赏 / 公会 |
| 报酬（已托管） | 接单者可见实得金额 |
| 起点 → 终点 | 文字描述或地点名 |
| 危险度 / 推荐等级 | 软提示 |
| 剩余时间 | 抢单/送达倒计时 |
| 发布者信誉 | 星级或完成单数 |

交互：**抢单**按钮 → 进行中 → **送达确认**（或系统自动）→ 报酬到账动画。

## 八、与 MiraWorld 世界观的结合点

- 任务不一定是「杀 10 只怪」，可以是：
  - **潮灯商会**：货运、报关、打听消息
  - **拾遗院**：鉴定碎片、拓印文献、实地测绘
- 报酬可以是：**铜钱、灯油、情报、声望、独家词条解锁**，而不只是金币。
- 叙事钩子：「你把院里的任务拆给港口的闲人，他们不知道自己在帮拾遗院挡哪一股势力。」

## 九、最小可行版本（MVP）

若要先做一版验证玩法，建议分两阶段：

**阶段 1：纯外卖式（系统派单）**

1. 系统向订单池投放 **跑腿类日常**（送达物品 A → 地点 B）
2. 玩家 **抢单 → 完成 → 系统发报酬**（无玩家发布）
3. 持单上限 1、超时回池、报酬托管与自动结算
4. 关联账号互接限制（简易版）

**阶段 2：叠加玩家悬赏**

5. 允许把 **1 类可拆分日常** 拆成 2～3 子任务进入同一订单池
6. 发布者预扣报酬，全部子单完成后原任务可提交

验证指标：抢单率、完成率、超时率、是否出现刷币嫌疑。

阶段 1 更简单，且能先验证「外卖模型」在本游戏是否好玩；阶段 2 再加玩家经济。

## 十二、除商品单、服务单外：现实中常见的订单类型

以下均可纳入「玩家 A → 系统 → 玩家 B」框架，按**是否适合 MiraWorld（文字、异步、系统验收）**标注优先级。

| 类型 | 现实例子 | 游戏内形态 | A 要什么 | B 做什么 | 系统角色 | 适合度 |
|------|----------|------------|----------|----------|----------|--------|
| **跑腿单** | 同城代办、取送文件 | 已有（外卖/信使） | 送到某物 | 行者取送 | 路线/物品验收 | ★★★ 首选 |
| **悬赏单** | 众包、任务平台 | 玩家拆单 / 调查委托 | 办成一事 | 接单完成 | 托管+验收 | ★★★ |
| **二手交易单** | 闲鱼、转转 | 玩家挂卖装备/材料 | 买闲置 | 卖家发货 | ** escrow 托管**，确认收货放款 | ★★★ |
| **预约单** | 餐厅订座、医院挂号 | 订镜湖驿茶位、NPC 时段 | 占一个时间槽 | 商家保留席位 | 时段库存、超时释放 | ★★☆ |
| **租赁单** | 租车、租设备 | 租信鸽、租探测仪 N 小时 | 短期使用权 | 出租方提供物品 | 到期自动收回、押金 | ★★☆ |
| **团购/拼单** | 拼多多、团购 | 5 人成团买低价补给 | 低价批量买 | 商家凑单发货 | 成团判定、失败退款 | ★★☆ |
| **定制/代工单** | 家具定制、裁缝 | 「按图纸做 3 件护符」 | 指定成品 | 工匠消耗材料制作 | 配方校验、品质随机（服务器 roll） | ★★☆ |
| **情报单** | 付费咨询、私家侦探 | 购买「某地点隐藏事件」线索 | 信息 | 情报贩子提交（系统校验是否已探索） | **防剧透分级**、信息真伪 | ★★☆ |
| **陪练/教学单** | 游戏陪玩、家教 | 带新手过副本文字关（软） | 陪同体验 | 老手聊天引导 | 仅撮合+评价，**不代打硬进度** | ★☆☆ 偏软 |
| **竞价单（反向拍卖）** | 装修招标 | A 发需求，多个 B 报价，A 选最低 | 择优成交 | 报价竞标 | 密封报价、截止时间开标 | ★★☆ |
| **拍卖单** | eBay、拍卖行 | 稀有遗物竞价 | 最高价者得 | 卖家上架 | 出价递增、防狙击 | ★★☆ |
| **订阅单** | 会员、包月奶 | 商会月卡每日领灯油 | 持续权益 | 系统/商家履约 | 周期扣费、权益发放 | ★☆☆ 后期 |
| **顺风车/载人** | 滴滴拼车 | 从灰烬港到镜湖驿「带一人」 | 到达某地 | 有车玩家/route | 同路线匹配 | ★☆☆ 可并入跑腿 |
| **担保/中介单** | 第三方担保交易 | 大额交易走系统冻结 | 安全成交 | 双方交付 | 条件满足才放款 | ★★★ 与二手单共用 |
| **票务单** | 演唱会门票 | 世界事件限量入场券 | 名额 | 系统/主办方 | 库存扣减、防重复购 | ★★☆ 活动用 |
| **借贷单** | 借条、网贷 | 游戏内借币 | 资金周转 | 出借 | 利息、违约 | ★ 经济风险大，慎做 |

### 12.1 建议分期纳入

| 阶段 | 订单类型 |
|------|----------|
| MVP | 跑腿单、系统派单 |
| v2 | 服务单、商品单（商家+骑手） |
| v3 | 二手托管交易、悬赏调查单 |
| v4 | 预约、租赁、定制、拍卖 |

不必一次做完；共用底层：**订单状态机 + 托管账户 + 系统验收器**。

## 十三、全程在线 + 软硬交互：设计原则、改进与漏洞

### 13.1 你们定的交互原则（建议写进规范）

```
硬交互（系统裁定）          软交互（人对人，系统不裁定成败）
─────────────────          ─────────────────────────────
下单、支付、抢单            聊天、议价话术、组队商量
背包增减、物品转移          角色扮演、情报「口述」（非绑定进度）
任务是否完成                陪玩式引导（不替对方点选项）
战斗/检定结果 roll          公会公告、留言
信誉、封禁、结算            好友、黑名单
```

**原则：凡影响资源、进度、货币的，一律服务器计算；聊天仅传播信息，不改变硬状态。**

好处：

- 减少「他说做完了」纠纷 —— 系统只认日志。  
- 减少外挂改本地数据 —— 浏览器里没有真金元宝。  
- 人机并行：多人同时点按钮，由服务器排队处理，结果一致。

### 13.2 在此原则下的改进空间

| 改进点 | 说明 |
|--------|------|
| **统一订单内核** | 商品/服务/跑腿/二手共用 `Order` 表 + `status` + `escrow_id`，避免每种单各写一套 |
| **事件溯源** | 每笔状态变更写 `order_events`（谁、何时、从哪状态到哪状态），方便查刷单 |
| **幂等提交** | 客户端带 `request_id`，防止双击「完成」结算两次 |
| **乐观 UI** | 网页先显示「提交中…」，等服务器确认后再变「已完成」，不本地先改钱 |
| **异步通知** | 完成后 WebSocket / 轮询 / **系统邮箱**入账，不必整页刷新（邮箱=被动查阅，非弹窗推送） |
| **软交互挂钩硬结果** | 例如情报单：B 只能提交系统预定义的「情报条目 ID」，不能自由输入改状态 |
| **分片订单池** | 按区域/类型分列表，减轻「全服一个大池」的性能与认知负担 |

### 13.3 仍可能出现的漏洞（修补清单）

| 漏洞 | 场景 | 修补 |
|------|------|------|
| **客户端伪造** | 改 JS 发包声称已送达 | **永远不信任浏览器**；只信带签名的 session + 服务端校验 |
| **重放攻击** | 同一完成请求连发多次 | 幂等键 + 订单状态机（仅 `in_progress` 可 → `done`） |
| **竞态抢单** | 两人同时抢一单 | 数据库 `UPDATE ... WHERE status=open` 行锁或乐观锁，只有一个成功 |
| **负值/溢出** | 报酬填 -99999 | 服务端类型与范围校验；用整数分（cents）存金额 |
| **时间作弊** | 改本机时间刷限时单 | **只用服务器时间** `now()` |
| **聊天诈骗** | 「线下转我币便宜」 | 提示+举报；硬货币禁止玩家直转或限额 |
| **情报剧透** | 卖家 texto 剧透主线 | 情报单只卖「已解锁条目」，自由文本不进任务系统 |
| **陪玩代打** | 软陪玩实则上号代点 | 账号不可共享；敏感操作二次验证；主线不可外包 |
| **库存超卖** | 两人同时买最后 1 件 | 事务内扣库存 `WHERE stock > 0` |
| **挂单 DDoS** | 恶意刷 10 万条订单池 | 发单频率限制、押金、信誉门槛 |
| **慢查询拖垮** | 订单池全表扫描 | 索引 `(status, type, created_at)`、分页、缓存热榜 |

### 13.4 「软交互」与「硬结果」的边界示例

| 玩家行为 | 类型 | 系统是否管 |
|----------|------|------------|
| A 在聊天里求 B「帮我送个东西」 | 软 | 否，除非走下单 |
| A 在平台点「发跑腿单」并托管报酬 | 硬 | 是 |
| B 聊天说「送到了」 | 软 | 否 |
| B 在游戏内到坐标点「交付」按钮 | 硬 | 是，校验坐标+物品 |
| 两人组队语音商量战术 | 软 | 否 |

## 十四、技术架构：谁在计算？如何支撑高并发？

> 针对 MiraWorld 当前与目标形态；与现有部署（静态网页 + 阿里云 + FastAPI 认证）对齐。

### 14.1 谁在计算？—— 一句话

| 内容 | 谁算 | 在哪算 |
|------|------|--------|
| 页面排版、动画、表单输入 | 浏览器 | 用户电脑/手机 |
| **登录、资源、订单、任务是否完成** | **云服务器** | **阿里云 8.133.252.224（及以后扩展）** |
| 静态 HTML/CSS/JS 文件 | 不「算」，只读取 | nginx 直接发给浏览器 |

**绝不能**把金币、背包、订单完成判定放在浏览器里算完再告诉服务器 —— 那样可被篡改。

当前项目现状：

```
浏览器 ──HTTP──► nginx ──► 静态文件（VitePress 构建产物）
                │
                └── /miraworld/api/* ──► FastAPI（认证等，已在跑）
```

商单/任务系统上线后，应继续走 **`/miraworld/api/` 或独立 game API**，逻辑全部在 **Python/FastAPI（或 Node）进程 + SQLite/PostgreSQL** 中执行。

### 14.2 一次「提交任务」实际发生什么

```
1. 玩家在网页点「交付」
2. 浏览器发 HTTPS 请求：POST /api/orders/123/complete（带 Cookie）
3. 云服务器：
   - 验证登录
   - 读数据库：订单状态、玩家位置、背包
   - 判定是否满足条件
   - 在一个事务里：改订单状态、扣物品、加钱、写日志
   - 返回 JSON { ok: true, reward: ... }
4. 浏览器根据返回更新界面
```

计算量很小（查库+规则），**瓶颈通常在数据库并发与网络**，不是网页算不动。

### 14.3 很多人同时操作，如何少卡顿、撑高并发？

#### 原则分层

| 层级 | 手段 |
|------|------|
| **静态资源** | CDN / nginx 缓存；JS/CSS 带 hash，长期缓存 |
| **API** | 无状态服务，可多进程（uvicorn workers） |
| **数据库** | 连接池；热点行用行锁/事务；必要时换 PostgreSQL |
| **读多写少** | Redis 缓存订单列表前几页、排行榜（后期） |
| **写操作** | 抢单、结算走**短事务**，避免长时间锁表 |
| **削峰** | 非实时逻辑进队列（Celery/Redis Queue）：发奖励邮件、统计 |
| **限流** | 每用户每秒 N 次请求，防脚本刷接口 |
| **分页** | 订单池永不一次拉全服；每页 20 条 |

#### 针对「抢单」高并发（重点）

```sql
-- 伪代码：只有一个玩家能抢到
UPDATE orders
SET status='claimed', worker_id=?
WHERE id=? AND status='open';
-- affected_rows == 1 才成功，否则返回「已被抢」
```

数据库保证**原子性**，比「先查再改」安全。

#### 网页侧减少「卡」的体验（不等于提高服务器算力）

- 按钮点击后 **loading**，禁止连点  
- 列表 **分页 / 虚拟滚动**，不一次渲染上万条  
- 用 **轮询 3～5 秒** 或 WebSocket 更新订单状态，而非整页 reload  
- 静态站点与 API 分离，nginx 不被 Python 拖慢  

#### 你们当前单机阶段的现实预期

| 规模 | 架构 | 说明 |
|------|------|------|
| **几十～几百** 同时在线 | 单台阿里云 + SQLite/PostgreSQL + 2～4 uvicorn workers | 足够 MVP |
| **上千** 同时在线 | PostgreSQL + Redis + 多 worker + 监控 | 需升级 |
| **上万** | 负载均衡、多机、读写分离、队列 | 远期 |

不必一开始过度设计；但**代码要写清：权威在服务端**，以后扩 worker 即可。

### 14.4 架构示意图（目标态）

```
┌─────────────┐     HTTPS      ┌─────────────┐
│   浏览器     │ ◄──────────► │    nginx      │
│  UI/动画     │               │  静态 + 反代   │
│  （不算账）   │               └──────┬──────┘
└─────────────┘                      │
                                     ▼
                              ┌─────────────┐
                              │  Game API   │  ← 订单、背包、任务判定
                              │  (FastAPI)  │
                              └──────┬──────┘
                                     │
                    ┌────────────────┼────────────────┐
                    ▼                ▼                ▼
              ┌──────────┐    ┌──────────┐    ┌──────────┐
              │ SQLite / │    │  Redis   │    │  队列    │
              │ Postgres │    │ (后期)   │    │ (后期)   │
              └──────────┘    └──────────┘    └──────────┘
```

聊天（软交互）可另做轻量频道服务，**不经过订单事务**，避免拖慢结算。

### 14.5 与现有账号系统的关系

- 已有：注册 / 登录 / JWT Cookie（`server/app.py`）  
- 商单系统应：**同一用户 ID** 关联订单、背包、信誉  
- 新接口一律 **登录后** 才可发单/抢单

## 十五、方案公司 → 产品公司 → 平台 → 用户（数字商品分账）

> 现实链路：方案公司给客户做方案 → 客户做成**线上产品**在网上卖 → 用户网页/手机下单付款 → 钱经**平台** → 给产品公司 → 产品公司再分给方案公司。  
> 商品是**纯线上数字商品**，无线下物流。以下映射到 MiraWorld 的 A↔系统↔B 体系。

### 15.1 现实角色对照

| 现实 | 做什么 | 游戏内映射 | 对应之前的身份 |
|------|--------|------------|----------------|
| **终端用户** | 网页下单、付钱、获得数字产品 | **玩家 C（购买者）** | 商单里的玩家 A（需求方） |
| **平台 / 支付系统** | 收款、托管、分账、规则 | **系统** | 始终居中 |
| **产品公司** | 拿方案做成可卖的产品，运营销售 | **玩家 B₂（产品方 / 发行商）** | 类似「注册商家」，但卖的是**数字货** |
| **方案公司** | 出方案、模板、设计，不直接面对终端用户 | **玩家 B₁（方案方 / 内容供应商）** | 新身份：**注册方案师** 或 认证创作者 |

注意：**此处的玩家 A 是购买者 C**；**方案方 B₁** 和 **产品方 B₂** 都是供给链上的 B，层级不同。

### 15.2 资金流（现实 → 游戏）

```
玩家 C 支付 100（买数字商品）
        │
        ▼
   ┌─────────┐
   │  系统    │  托管 100，扣平台抽成（例 10）→ 平台收入 10
   └────┬────┘
        │ 可分配池 90
        ├──────────────────┐
        ▼                  ▼
  产品方 B₂ 得 63      方案方 B₁ 得 27
  （例 70% 可分配）    （例 30% 可分配，或按授权合约）
```

现实中「产品公司再分给方案公司」在游戏里可以做成：

- **方式 1（推荐）**：系统**一次分账** —— C 付款时按商品绑定的 `royalty_split` 自动拆给 B₂ 和 B₁，B₂ 无需手动转款（防赖账、防刷）。  
- **方式 2**：先全给 B₂，系统定期把方案授权费转 B₁（复杂，易纠纷，不推荐 MVP）。

### 15.3 业务流（数字商品，无线下配送）

```
① 方案方 B₁
   制作「方案资产」：任务模板、剧情模块、店铺皮肤、道具配方、服务流程脚本…
   上架到「方案市场」或授权给特定产品方

② 产品方 B₂
   购买/获得方案授权 → 在系统内配置成「可售商品」
   （例：礼包、月卡、调查委托包、装饰、情报包）

③ 系统
   审核（可选）→ 生成商品 SKU → 挂到 B₂ 的店铺 / 全服商城
   记录：哪个 SKU 绑定了哪个方案 ID、分账比例

④ 玩家 C
   浏览网页商城 → 下单 → 支付（系统托管）

⑤ 系统
   即时交付数字商品（进背包 / 解锁权益 / 发放服务次数）
   按合约分账给 B₂、B₁，记台账
```

**没有骑手环节** —— 这是**数字商品单**，交付是系统 `grant_item()`，不是商品单里的「备餐+配送」。

### 15.4 与已有订单类型的关系

| 已有类型 | 本模型 | 区别 |
|----------|--------|------|
| **商品单（外卖）** | 实物/需备货+配送 | 有商家+骑手，要库存与送达 |
| **服务单** | 人提供服务 | 服务员履约，可能远程/上门 |
| **本模型：数字商品单** | 方案驱动的产品 | **无物流**；交付=系统发数据；**两级 B 分账** |

可并存：外卖式卖「实体游戏内道具」用商品单；卖「委托包/剧情 DLC/模板权益」用数字商品单。

### 15.5 系统需要多记什么（数据模型提示）

每个可售 **数字商品 SKU** 建议绑定：

| 字段 | 说明 |
|------|------|
| `seller_id` | 产品方 B₂ |
| `blueprint_id` | 方案方 B₁ 的方案资产 ID |
| `price` | C 支付价 |
| `platform_fee_rate` | 平台抽成 % |
| `royalty_rate` | 方案方从「可分配池」拿的 %（或固定金额） |
| `deliverable` | 交付物：物品 ID 列表、服务次数、解锁 flag |

一笔成交写入：

- `orders`（C 的购买记录）  
- `ledger_entries`（C→托管→平台、托管→B₂、托管→B₁ 多条流水）  

**全程系统算、系统分**，人不私下转账。

### 15.6 方案资产是什么（MiraWorld 举例）

| 方案资产 | 产品方做成什么卖 | 购买者得到什么 |
|----------|----------------|----------------|
| 「灰烬港调查」任务蓝图 | 「调查委托包」×5 次 | 5 次指定类任务入口 |
| 店铺 UI 主题方案 | 「镜湖皮肤」 | 店铺外观 |
| 合成配方方案 | 「工匠礼包」 | 配方解锁 + 材料 |
| NPC 对话包方案 | 「某角色支线解锁券」 | 剧情章节 |

方案方**不必须**自己开店；可以只做方案，让多个 B₂ 授权销售（像现实方案公司服务多个客户）。

### 15.7 授权与版权（防漏洞）

| 风险 | 系统规则 |
|------|----------|
| B₂ 卖了不付方案费 | **强制分账**，从 C 付款里自动扣给 B₁ |
| B₁ 方案抄袭 | 方案市场上架审核 + 举报；副本检测（后期） |
| B₂ 私自改方案超范围卖 | SKU 只能绑定已授权 `blueprint_id`，交付范围系统校验 |
| B₁ B₂ 同一人刷分账 | 允许但分账透明；关联号异常监控 |
| C 退款 | 数字商品是否可退：MVP 建议**不可退**或 24h 内且未使用可退，系统回滚权益并反向分账 |

### 15.8 和「玩家商单 A↔系统↔B」的统一说法

可以把整条链看成 **两条线叠加**：

```
【供应链】  方案方 B₁ ──授权──► 产品方 B₂ ──上架 SKU──► 系统商城
【消费链】  购买者 C ──付款──► 系统托管 ──分账──► B₂ + B₁ + 平台
【交付】    系统 ──发放数字资产──► C
```

系统始终是枢纽：**不方案公司直接面对终端用户收钱**（除非 B₁ 自己也是 B₂ 一人全包，此时分账比例里 B₁+B₂ 合并为同一账号）。

### 15.9 MVP 怎么做最简

若验证「方案→产品→卖」：

1. **方案**：系统预置 1 个任务模板（甚至先写死在服务器，暂不开放玩家创作）  
2. **产品**：1 个注册商家 B₂ 把模板包成「调查包」SKU  
3. **购买**：玩家 C 花币购买 → 系统加次数 → 自动分 70/30 给 B₂ 和「系统方案池」  
4. 暂不开放玩家当 B₁，方案方先用系统占位  

验证通过后再开 **方案市场** 让玩家 B₁ 上传模板。

### 15.10 待讨论

- [ ] 方案授权：**独家**（只一家 B₂ 能卖）还是 **非独家**（多家可卖，B₁ 按销量提成）？  
- [ ] 分账比例：B₁ 与 B₂ **谈判**还是平台**固定档位**？  
- [ ] 数字商品是否允许玩家 C 二次转卖（二手单）？

## 十八、系统作「芯片方」：SDK → 方案 → 产品 → 销售（可裁剪）→ 定价与灯市

> 叠合前文：外卖商单、A↔系统↔B、数字商品分账。本节把 **系统 = 自研芯片 + SDK**，方案公司 = 用 SDK 开发，客户 = 包装上架；并讨论 **砍掉销售层**、**代购/限价单**、**期货**，以及一个较新的总架构观点。

### 18.1 全栈映射（从芯片到终端）

```
                            │ SDK 授权 / 模板语法
                            ▼

└───────────────────────────┬─────────────────────────────────┘
                            │ 授权 / 定制交付
                            ▼
┌─────────────────────────────────────────────────────────────┐
│  L2  B₂ 产品方（客户 / 发行商）                                │
│      产出：Product SKU（品牌、包装、定价策略、上架信息）          │
│      绑定 blueprint_id，调用系统「铸造」可售单元                 │
└───────────────────────────┬─────────────────────────────────┘
                            │ 可选分支
              ┌─────────────┴─────────────┐
              ▼                           ▼
┌──────────────────────┐    ┌──────────────────────┐
│ L3a 多销售方（代售）   │    │ L3b 裁剪：B₂ 直售     │
│ 代销、渠道、导购       │    │ B₂ 直接挂全服商城      │
│ 佣金在分账里体现       │    │ MVP 推荐这条           │
└──────────┬───────────┘    └──────────┬───────────┘
           │                           │
           └─────────────┬─────────────┘
                         ▼
┌─────────────────────────────────────────────────────────────┐
│  L4  C 终端购买者                                            │
│      一口价购买 / 限价求购 / 期货认购 → 系统交付数字权益         │
└─────────────────────────────────────────────────────────────┘
```

| 现实 | 栈层 | 游戏内身份 | 产出物 |
|------|------|------------|--------|
| 自研芯片公司（或平台自有芯片） | L0 | **系统** | SDK、原子能力、运行时 |
| 方案公司 | L1 | **B₁ 方案方** | Blueprint 蓝图 |
| 产品公司 | L2 | **B₂ 产品方** | Product SKU |
| 经销商（可不要） | L3 | **B₃ 销售方**（可选） | 渠道链接、代售挂单 |
| 手机用户 | L4 | **C** | 付款、获得权益 |

### 18.2 L0：系统当「芯片方」——SDK 里有什么

系统不卖「完整任务包」，只卖**能力边界**（像芯片指令集）：

| SDK 原子（举例） | 说明 | B₁ 能做什么 |
|------------------|------|-------------|
| `VisitLocation(id)` | 到达地点 | 组合成调查链 |
| `CollectItem(id,n)` | 收集物品 | 跑腿、收集类 |
| `DialogueChoice(tree)` | 对话树 | 剧情类 |
| `EscrowReward(split)` | 分账模板 | 嵌入多方分成 |
| `TimeLimit(h)` | 时限 | 限时委托 |
| `GrantUnlock(flag)` | 解锁 | 卖 DLC 式权益 |

**B₁ 用 SDK「开发」= 在编辑器里拖拽/配置这些原子**，生成一份 **Blueprint JSON**（或可视化方案），提交给系统 **校验**：

- 是否只用已授权原子  
- 奖励是否超经济上限  
- 是否触碰主线禁区  

校验通过 → 蓝图进入 **方案库**，可授权给 B₂。

> 自研芯片公司可映射为：未来开放「第三方模组 SDK」；MVP 阶段 **系统独占 L0**，避免生态失控。

### 18.3 L1 → L2：方案如何「交付」给客户（B₂）

不是发邮件传文件，而是 **系统内授权记录**：

```
B₁ 在「方案工作台」完成 Blueprint v1.2
    → 提交审核（或自动校验）
    → 生成 blueprint_id = BP-7f3a…
    → B₁ 对 B₂ 发起「授权」：
         - 独家 / 非独家
         - 地域（全服 / 某势力）
         - royalty_rate（B₁ 从每笔售价拿 %）
         - 是否允许 B₂ 再包装子 SKU
    → B₂ 账户出现「已授权方案」列表
```

B₂ **拿不到可篡改的源码文件**，只有 **运行时许可证 + 配置壳** —— 防止 B₂ 绕过 B₁ 分账（和芯片厂只给 SDK 不给芯片图纸类似）。

### 18.4 L2：客户如何「包装」并上架

B₂ 在 **产品工作台** 操作：

| 步骤 | 内容 |
|------|------|
| 选蓝图 | 从已授权 `blueprint_id` 中选 |
| 包装 | 商品名、描述、图标、 lore 文案、捆绑次数（如「调查包×5」） |
| 定价模式 | 见 §18.6（一口价 / 订单簿 / 期货） |
| 铸造 SKU | 系统生成 `product_id`，绑定 blueprint + 分账表 |
| 上架 | 全服商城 / 仅店铺 / 仅邀请链接 |

**裁剪销售层（L3b）**：B₂ 点「全服上架」→ C 直接在商城买，无需 B₃。  
**保留销售层（L3a）**：B₂ 设 `channel_rate`，B₃ 代售链接成交后系统三分账 `C→B₃→B₂→B₁→平台`。

MVP 建议：**先 L3b 直售**，代售后期再加。

### 18.5 多销售方 vs 直售（怎么选）

| 模式 | 优点 | 缺点 | 适用 |
|------|------|------|------|
| **B₂ 直售** | 链路短、分账简单、少纠纷 | B₂ 要自己运营流量 | MVP、小众精品 |
| **多 B₃ 代售** | 渠道裂变、仿分销 | 多一层分账、防窜货 | 大规模运营期 |
| **系统统一货架** | 曝光公平、搜索方便 | B₂ 同质化 | 配合推荐算法 |

规则建议：**同一 SKU 要么直售，要么代售，配置时二选一或设渠道上限**，避免同一商品多渠道乱价。

### 18.6 定价：一口价、代购限价单、期货（不是随便当股价）

你提到的「标低价求购 / 标高价出售 / 像股票涨跌」需要拆开：

#### A. 一口价（零售）

- B₂（或 B₃）设 **固定售价**  
- C 点买即成交  
- **没有 K 线**，价格由发行方决定  
- 对应：App Store 标价、游戏商城礼包  

#### B. 限价单 / 订单簿（代购、代售）

- **买单**：C（或收购方）挂「我愿出 ≤ 80 收购此权益」  
- **卖单**：持有者挂「我愿以 ≥ 100 出售」  
- **系统撮合**：买价 ≥ 卖价时成交（类似股票限价单，但**标的是该数字商品/权益**，不是公司股权）  
- 价格可波动，但波动来自**挂单撮合**，不是自动生成股价  

这不是「股票」，而是 **「灯市订单簿」** —— 二手权益交易所。

防炒：设 **涨跌停 / 单日成交量上限 / 只有可转让 SKU 能挂单**。

#### C. 期货 / 预售

- B₂ 卖「下月开放的剧情包」，现在付钱，**到期系统交割**权益  
- 适合未做完的内容、季节活动  
- 可转让「期货凭证」（高级，易投机，需慎重）  

#### D. 不建议初期做的

- **连续竞价股价**：需要做市商、流动性，文字游戏生态太小，易被人操纵  
- **自由涨价零售**：若 B₂ 说卖 100 就该 100；波动应限定在 **二级市场订单簿**，不要零售端和炒股混在一个 UI  

| 售卖方式 | 谁定价 | 是否波动 | 系统复杂度 |
|----------|--------|----------|------------|
| 一口价零售 | B₂ | 否 | 低 ★ MVP |
| 限价单/订单簿 | 买卖双方 | 是（撮合价） | 中 |
| 期货/预售 | B₂ 定发行价，二级可转让 | 凭证可波动 | 高 |

### 18.7 一次购买的分账（含可选 B₃）

C 花 100 买一口价 SKU（示例）：

```
100 托管
 ├─ 平台 8
 ├─ B₁ 方案 royalty 15  （按 blueprint 合约）
 ├─ B₃ 渠道 7           （若走代售；直售则无）
 └─ B₂ 产品方 70
```

订单簿成交的二手单，还要约定：**royalty 是否二次收取**？

- **方案 A**：二手只分给**当前卖方 + 平台**，B₁ 不再拿（常见）  
- **方案 B**：每次转手 B₁ 拿微量「版税」（NFT 式，刺激方案方）  

建议 MVP：**二手不再分 B₁**，避免算账爆炸。

### 18.8 新奇观点：**「潮灯协议栈」—— 系统只做芯片，不做超市**

把前面所有讨论收成一句话：

> **MiraWorld 不是「一个商城 + 一堆任务」，而是一条「可编程任务与数字资产」的协议栈；系统像芯片厂提供 SDK 与运行时，玩家公司在栈上各层创业。**

| 传统做法 | 潮灯协议栈 |
|----------|------------|
| 系统直接设计所有任务 | 系统只提供 **任务原子 + 验收 + 分账管道** |
| 一个商城列表 | **铸造层**（Blueprint→SKU）+ **灯市**（零售 + 可选订单簿） |
| 玩家只能接任务 | 玩家可以是 B₁/B₂/C，甚至 B₃ |
| 价格策划写死 | **双轨定价**：发行一口价 + 权益二级限价单（可选） |
| 人与人物交易 | **硬走链**：每笔带 `provenance`（血统） |

**血统（Provenance）**：每个到 C 手里的权益，日志里写着：

`L0:SDK v3 → L1:BP-7f3a by 玩家甲 → L2:SKU-22 by 玩家乙 → 成交 tx-991`

好处：

- 抄袭、纠纷可追  
- B₁ 方案价值可量化（被多少 SKU 引用）  
- 叙事上像「遗物有来历」，贴合 MiraWorld  

**灯市**：世界观里统一交易所名 —— 零售柜 + 订单簿墙 + 期货屏，都在「潮灯商会」名下，玩家好理解。

### 18.9 与商单体系（外卖/服务）如何共存

同一套 **L0 运行时**：

| 上层产品形态 | 用的栈 |
|--------------|--------|
| 外卖式跑腿 | SDK 原子 `Deliver(A→B)` + 骑手抢单 |
| 服务上门 | SDK 原子 `ServiceAt(loc)` |
| 数字商品零售 | Blueprint → SKU → 一口价 |
| 二手/代购 | 同一 SKU 的 **可转让实例** + 订单簿 |
| 期货 | SKU 的 `delivery_at` 未来交割 |

**不是多套系统**，是 **同一芯片，不同固件（Blueprint 类型）**。

### 18.10 实施路线（极简）

| 阶段 | 内容 |
|------|------|
| P0 | L0 内置 5 个任务原子；系统直售 1 个 SKU（无 B₁/B₂ 玩家） |
| P1 | 开放 B₂ 包装上架（蓝图仍系统出） |
| P2 | 开放 B₁ 方案工作台 + 授权给 B₂ |
| P3 | 灯市订单簿（二手限价单） |
| P4 | 期货 / 代售渠道 B₃ |

### 18.12 方案方（B₁）如何用 SDK 满足客户需求 —— 完整工作流

> 问题：系统出了「芯片/SDK」，方案公司拿到之后，**具体怎么开发**？怎么把 **B₂（客户）的功能需求** 变成可交付、可上架、可运行的方案？

#### 第一步：分清「客户需求」和「SDK 能做什么」

B₂ 客户说的往往是**业务语言**；B₁ 要翻译成 **SDK 原子组合**。

| B₂ 客户说（需求） | B₁ 理解成（功能） | SDK 层实现（原子） |
|-------------------|-------------------|---------------------|
| 「我想卖 5 次调查玩法」 | 可重复执行的调查流程 ×5 | `Repeat(BlueprintCore, 5)` + `GrantToken` |
| 「玩家要去灰烬港找线索」 | 地点 + 探索 + 掉落 | `VisitLocation` + `DialogueChoice` + `CollectItem` |
| 「做完给声望和钱」 | 奖励曲线 | `Reward(currency, rep)` + `EscrowSplit` |
| 「只有买过的人才能做」 | 门禁 | `RequireUnlock(flag)` |
| 「限时 48 小时」 | 时间约束 | `TimeLimit(48h)` |
| 「我要分 30% 给方案方」 | 分账（系统可自动） | Blueprint 元数据 `royalty_rate` |

B₁ 的核心能力：**需求分析 + 原子编排**，不是写服务器代码（硬逻辑仍由系统执行）。

#### 第二步：标准接单流程（方案公司视角）

```
① 接洽（软）
   B₂ 提出需求：目标用户、玩法、定价区间、上线时间
   B₁ 评估：SDK 是否覆盖、要不要申请「扩展原子」（向系统提工单）

② 签方案单（硬，走系统）
   B₂ 在平台发「方案委托单」→ 托管定金/全款
   写明：交付物类型（Blueprint）、验收标准、版税比例、是否独家

③ 设计（B₁ 在方案工作台）
   见下文「编辑器三步」

④ 仿真 / 试玩（硬）
   系统提供「沙盒账号」跑一遍 Blueprint，B₁ 自测，B₂ 可旁观链接

⑤ 交付（硬）
   提交 Blueprint v1.0 → 系统校验 → 写入方案库
   自动向 B₂ 账户写入「授权」记录（可配置 royalty）

⑥ 验收（硬）
   B₂ 点验收 或 7 日无申诉自动过 → 释放托管款给 B₁
   若不合格：退回修改，版本 v1.1…

⑦ 后续（B₂ 侧）
   B₂ 拿授权去「产品工作台」包装 SKU、上架（§18.4）
   B₁ 不替 B₂ 上架零售（除非另签代运营单）
```

人与人在 ① 可聊天；**从 ② 起全部系统单据**。

#### 第三步：方案工作台 —— B₁ 实际「开发」界面（建议）

类比：芯片厂给的是 IDE + 指令集，不是帮方案公司写 App。

**（1）需求卡（Requirements）**

B₁ 先填结构化需求（可从 B₂ 委托单导入）：

- 玩法类型：调查 / 护送 / 收集 / 纯叙事…  
- 预计时长、难度、可重复次数  
- 奖励上限（系统按经济表自动 cap）  
- 涉及地点、NPC、物品 ID（从世界百科选，防编造无效 ID）  

**（2）编排器（Composer）—— 两种 UI 择一或并存**

| 模式 | 适合谁 | 操作 |
|------|--------|------|
| **表单向导** | 新手方案方 | 选模板「调查类」→ 填地点/对话/奖励 → 生成 Blueprint |
| **节点图** | 高级方案方 | 拖拽 `Visit`→`Dialogue`→`Branch`→`Reward` 连线 |

底层都是同一份 **Blueprint JSON**，系统只认 JSON，不认人。

**（3）模拟器（Simulator）**

- 「用测试角色跑一遍」：系统在沙盒执行，**不污染正式经济**  
- 输出：通过率、平均耗时、奖励是否超标、有无死胡同  
- 红灯项必须修完才能提交交付  

#### 第四步：Blueprint 文件里有什么（概念模型）

```yaml
blueprint:
  id: BP-7f3a
  sdk_version: "3.1"          # 绑定芯片版本，升级需回归测试
  author: B1_player_id
  type: investigation         # 模板类型
  nodes:                      # 状态机 / 节点图
    - id: start
      atom: VisitLocation
      params: { location: ashen_harbor }
    - id: talk
      atom: DialogueChoice
      params: { tree: dialog_ash_01 }
    - id: end
      atom: GrantReward
      params: { rep: 10, coin: 50 }
  edges: [ start→talk, talk→end ]
  meta:
    royalty_rate: 0.30
    license: non_exclusive
  deliverables:               # B₂ 包装 SKU 时可用的「权益壳」
    - grant: quest_run_token
      count: 5
```

B₂ **看不到**完整 `nodes` 源码（防抄袭方案、防绕过版税），只看到：

- 玩法摘要、时长、可配置外壳（商品名、售价）  
- 试玩链接  

#### 第五步：SDK 如何「限制又赋能」方案方

| 系统规则 | 对方案公司的意义 |
|----------|------------------|
| 只能用已发布原子 | 做不出越权玩法，但组合空间仍很大 |
| 经济上限 | 不能设计破坏平衡的奖励 |
| 世界百科 ID | 地点/NPC 必须存在，保证能跑 |
| 主线禁区列表 | 不能动核心剧情节点 |
| 版本兼容 | `sdk_version` 升级时旧蓝图可继续跑或提示迁移 |

若 B₂ 需求 **超出 SDK**：B₁ 向系统提「新原子申请」（类似向芯片厂要新指令），**系统审核后**才进下一版 SDK —— 避免每个方案方改服务器代码。

#### 第六步：满足客户需求的三类交付包

| 交付级别 | 内容 | B₂ 拿到后 |
|----------|------|-----------|
| **标准包** | Blueprint + 默认 5 次权益壳 | 自己包装 SKU |
| **定制包** | Blueprint + B₁ 帮填好 SKU 草稿 | B₂ 改价上架即可 |
| **全托管包** | Blueprint + SKU 已上架（另签合同） | B₁ 代运营，B₂ 只收钱 |

MVP 只做 **标准包**。

#### 第七步：和「芯片厂」系统的长期关系

```
系统发版 SDK 3.2（新增原子 Foreshadow）
    → B₁ 方案工作台提示「新能力」
    → B₁ 用新原子给客户做「伏笔类」调查包
    → 旧 Blueprint 仍跑在 3.1 运行时（兼容层）
```

方案公司**不需要部署服务器**；所有「开发」= 在浏览器里编排 + 系统沙盒验证 + 提交入库。

#### 18.12.1 一图流（B₁ 视角）

```
B₂ 功能需求（业务话）
      │  B₁ 翻译
      ▼
需求卡 + 选模板
      │
      ▼
方案工作台编排（SDK 原子）
      │
      ▼
沙盒试玩 ←── 系统校验（经济/权限/死锁）
      │
      ▼
提交 Blueprint → 授权给 B₂
      │
      ▼
B₂ 验收付款 → B₂ 自行包装 SKU → C 购买
      │
      ▼
每笔成交：系统按 royalty 自动分给 B₁
```

## 十九、小结（协议栈）

| 层级 | 角色 | 关键动作 |
|------|------|----------|
| L0 | 系统（芯片/SDK） | 原子能力、校验、运行、分账 |
| L1 | B₁ 方案方 | 用 SDK 设计 Blueprint，授权 B₂ |
| L2 | B₂ 产品方 | 包装 SKU、定价、上架 |
| L3 | B₃ 销售方（可选） | 代售；MVP 可裁剪 |
| L4 | C | 一口价买 / 限价单撮合 / 期货认购 |

| 定价 | 本质 |
|------|------|
| 零售一口价 | B₂ 标价，不炒 |
| 订单簿 | 代购代售，**像限价单不像股票** |
| 期货 | 先付后交割，可另开二级 |

**新奇主轴**：做 **协议栈 + 血统 + 灯市双轨定价**，而不是做一个大而全的固定商城。

## 二十、线上交付：系统作「开源引擎 + 云服务」，游戏公司作发行商（Steam 式）

> 与 §十五～§十八 的「方案蓝图线下式授权交付」互补。本节讨论更贴近真实游戏业：**系统 ≈ 虚幻引擎 + 云端 API**；**游戏公司**在平台上做完整游戏；**商城 ≈ Steam**（购买、游玩、评价、2 小时退款）。**模组延后**，不在本期范围。

### 20.1 两种交付范式对照

| 维度 | 偏线下（前文） | 偏线上（本节） |
|------|----------------|----------------|
| 系统角色 | 芯片/SDK、方案校验 | **引擎 + 运行时托管 + 商店** |
| 创作者 | B₁ 方案方、B₂ 产品方 | **游戏公司（Studio）** |
| 交付物 | Blueprint 授权、SKU 包装 | **可运行的 Game 包**，上架即玩 |
| 消费者体验 | 买权益/次数包 | **买游戏 → 进库 → 开玩** |
| 平台参照 | 方案外包、授权合同 | **Steam、Itch、Epic Store** |

两者可共存：Studio 内部仍可用 Blueprint/SDK 做关卡；对外卖的是 **整款游戏**。

### 20.2 角色映射（游戏业版）

| 现实 | 游戏内 / 平台内 | 说明 |
|------|-----------------|------|
| 虚幻引擎（开源）+ Epic 云服务 | **系统（L0）** | 引擎、编辑器、API、服务器、商店 |
| 游戏开发公司 | **Studio（开发商）** | 注册工作室，组团队，发游戏 |
| 编剧 / 外包文案 | **可雇用的创作者** | 走服务单或 Studio 内部分账 |
| Steam | **潮灯游戏库 / 商城** | 陈列、购买、库、评价 |
| 玩家 | **C（玩家）** | 购买、游玩、评测、退款 |

```
┌─────────────────────────────────────────────────────────┐
│  系统 = 引擎出品方 + 云厂商                               │
│  · MiraEngine（类比 UE）：场景、剧本、任务、UI 模块        │
│  · Cloud API：存档、账号、支付、匹配、统计、反作弊         │
│  · Store API：上架、定价、库、评价、退款、游玩时长         │
└────────────────────────┬────────────────────────────────┘
                         │ 用引擎开发 + 调用 API
                         ▼
┌─────────────────────────────────────────────────────────┐
│  Studio 游戏公司                                         │
│  · 看市场：什么题材/玩法热销（平台数据面板）              │
│  · 选 API：要存档？要排行榜？要内购？                      │
│  · 雇人：编剧、关卡、美术（服务市场或成员分成）            │
│  · 发布：提交 Game Build → 审核 → 商城上架                │
└────────────────────────┬────────────────────────────────┘
                         │ 上架
                         ▼
┌─────────────────────────────────────────────────────────┐
│  潮灯商城（Steam 式）                                    │
│  C：浏览 → 购买 → 游戏库 → 启动 → 评价 / 退款            │
└─────────────────────────────────────────────────────────┘
```

### 20.3 系统作为「引擎 + 服务器」提供什么 API

游戏公司**不自建服务器**（MVP），像用 UE + PlayFab 一样，按需调用：

| API 类别 | 能力（举例） | Studio 用来做什么 |
|----------|--------------|-------------------|
| **核心运行时** | 加载 Game Build、场景、存档 | 游戏能跑 |
| **叙事 / 任务** | Blueprint 运行时、对话树 | 剧本落地 |
| **账号与库** | `owns(game_id)`、游戏库 | 买了才能玩 |
| **经济** | 托管支付、分账、版税 | 卖游戏、给编剧分钱 |
| **社交（软）** | 评价、点赞、关注 Studio | 口碑传播 |
| **数据** | 销量、游玩时长、留存 | Studio 看行情调策略 |
| **合规** | 内容审核、年龄标签 | 上架前检查 |
| **退款** | 游玩时长累计、退款窗口 | §20.6 |

引擎开源（或部分开源）的含意：

- Studio 可本地 **Studio Editor** 编排内容（类似 UE Editor）  
- **联机与商业逻辑**走系统 API，防止改客户端作弊  
- Build 提交到平台后，由 **系统 CDN + 运行时** 分发给玩家浏览器  

### 20.4 游戏公司如何从 0 到 1 做出一款卖得出的游戏

#### （1）看市场（行情）

平台给 Studio **匿名聚合数据**（不是偷玩家隐私）：

- 标签热度：调查、恐怖、经营…  
- 价位带：￥X～￥Y 销量最好  
- 评价关键词：「剧情」「太短」「耐玩」  

Studio 据此定：**题材 + 定价 + 体量**（短篇 2h vs 长篇 20h）。

#### （2）定能力边界 —— 选哪些 API

| 游戏目标 | 要开的 API |
|----------|------------|
| 纯单机文字冒险 | 存档 + 库 + 支付 |
| 带排行榜 | + Leaderboard |
| 可雇佣编剧协作 | + 协作草稿 + 分账 |
| 含内购 DLC | + IAP + Blueprint DLC 槽位 |

**用不上的 API 不调用** = 省复杂度，也像真实项目控 scope。

#### （3）制作内容

- **程序 / 编排**：Studio 成员用引擎编辑器拼场景、任务流  
- **剧本**：自有或 **雇编剧**（发服务单：「写 3 万字灰烬港支线，报酬 5000 币」）  
- **试玩**：Studio 内测 → 提交 **Beta Build** → 小范围封测（可选）  

#### （4）提交与上架

```
Studio 提交 Game v1.0
  → 系统校验：Build 可启动、无违禁、API 声明完整
  → 商店页：名、图、描述、标签、价格、是否支持退款
  → 审核通过 → 公开发售
```

#### （5）收入与再投资

```
C 购买 ￥48
  → 平台抽成（例 30%，可调）
  → Studio 账户 ￥33.6
  → 若剧本约定 royalty：自动划 ￥5 给编剧
  → Studio 用余额继续雇人、做 DLC、做下一款
```

剧本「受欢迎」体现在：**游戏好评多 → 销量高 → 编剧 royalty 多**；也可单独给 **剧本点赞**（加权进推荐）。

### 20.5 编剧 / 外包如何嵌进 Studio（线上协作）

| 方式 | 流程 |
|------|------|
| **服务单** | Studio 发单 → 编剧接单 → 交付文稿/Blueprint 节点 → 系统验收 → 付款 |
| **成员分成** | 编剧进 Studio 团队，`Game` 元数据写 `revenue_share` |
| **悬赏** | 「征稿比赛」，最佳剧本获赏金 + 署名 |

硬交互：**文稿绑定到 Game 版本**；软交互：聊天改稿。

### 20.6 Steam 式基础体验（MVP 范围）

**本期做：**

| 功能 | 系统行为（全在服务器） |
|------|------------------------|
| **浏览商城** | 标签、搜索、价格、好评率、简介 |
| **购买** | 托管支付 → `library` 写入 `owns(game_id)` |
| **游戏库** | 已购列表，一键「开始游戏」 |
| **启动游玩** | 浏览器加载 Build（或内嵌运行时），**累计 `playtime_seconds`** |
| **评价** | 仅 **已购买且游玩 ≥ N 分钟** 可评（防刷好评）；星级 + 短评 |
| **退款** | 见下 |

**本期不做（延后）：**

- 模组 Workshop  
- 创意工坊上传  
- 家庭共享、礼物（可后期）  

#### 退款规则（对标 Steam，可简化）

建议政策（写入用户协议，**服务器强制执行**）：

```
可退款条件（同时满足）：
  1. 购买后 ≤ 14 天内（或 7 天，MVP 可缩短）
  2. 累计游玩时间 < 2 小时（120 分钟）
  3. 未因作弊被封禁
  4. DLC 等特殊商品单独声明（MVP 可先只做本体）

退款后：
  - 移除 library 访问权
  - 撤销未锁定的成就（若有）
  - 资金：平台已收部分按规则退；Studio 分成扣回
  - 该用户对此游戏的评价删除或标记无效
```

**试玩两小时还能退款** = 玩家可在 **低游玩时长内反悔**；超过 2h 或超期则不可退。

游玩时长 **只信服务器计时**（会话心跳），不信客户端上报。

#### 「试玩」与「退款」区别

| 概念 | 说明 |
|------|------|
| **购买后退款** | 先全款买，2h 内可退（Steam 模型） |
| **免费 Demo**（可选后期） | 未购买可玩第一章；不买也能玩一部分 |

MVP 先做 **购买 + 2h 退款**，Demo 可后加。

### 20.7 与「潮灯协议栈」的统一

线上模型不是替换线下，是 **多一层**：

```
L0  系统引擎 + Cloud API + Store
      │
      ├─► Studio 发完整 Game（线上主路径）
      │
      └─► 仍可用 Blueprint 做关卡模组 / DLC / 内购内容
            │
            └─► 旧模型：B₁ 方案、B₂ SKU 仍可服务「只做内容包」的小团队
```

**新奇整合观点**：

> **同一平台，两种上架形态**  
> - **Game**（整款，Steam 式，库+退款+评测）  
> - **Content Pack**（蓝图/SKU，轻量，走灯市一口价或订单簿）  
>  
> Studio 是大厨做整桌菜；B₁/B₂ 是供应食材与配方。共用 L0，不同货架。

### 20.8 数据模型提示（Store 最小集）

| 实体 | 关键字段 |
|------|----------|
| `studios` | 工作室名、成员、余额 |
| `games` | studio_id、build_url、price、tags、status |
| `purchases` | user_id、game_id、paid_at、refunded |
| `play_sessions` | purchase_id、duration_seconds（累计） |
| `reviews` | user_id、game_id、rating、text、eligible |
| `revenue_splits` | game_id → studio / writer / platform |

### 20.9 Studio 工作流一图流

```
看行情 → 立项 → 选 API → 引擎内开发
              │
              ├─ 自写剧本
              └─ 雇编剧（服务单）
              │
              ▼
         内测 Build
              │
              ▼
    提交审核 → 商城上架 → 营销（评价/推荐）
              │
              ▼
    C 购买 → 游玩（计时）→ 评价
              │
              ├─ <2h 退款 → 退库
              └─ 留存 → Studio 收入 → 再投资下一款
```

### 20.10 MVP 建议（仅 Steam 基础体验）

1. 系统预置 **1 款示范 Game**（官方 Studio）  
2. 开放 **1 个注册 Studio**，用编辑器做 **1 款短篇** 上架  
3. 商城：购买、库、启动、**服务端计时**  
4. 评价：购后且游玩 ≥10 分钟可评  
5. 退款：14 天内且游玩 <2h  
6. **不做**：模组、订单簿、期货、多 Studio 竞争排行（可后加）

## 二十一、小结（线上 + 线下双轨）

| 轨道 | 交付物 | 消费者体验 | 参照 |
|------|--------|------------|------|
| **线下式** | Blueprint / SKU | 买权益包 | 方案授权、数字商品 |
| **线上式** | Game Build | 买游戏、进库、玩、评、退 | Steam |

| 系统 | 引擎 + API + 商店 + 游玩计时 + 退款裁判 |
| Studio | 看行情、开发、雇编剧、上架、收钱 |
| C | 商城购买、游戏库、≥2h 不可退（政策内） |
