# 实现架构与模块划分（开发者定夺版）

> 状态：**可开工**的实现路线  
> 记录时间：2026-09-12  
> 原则：**单体模块化、SQLite、配置驱动世界、MVP 砍到能跑通一碗面**  
> **首发产品范围以 [29-MVP发布会与路线图](./29-MVP发布会与路线图.md) 为准**（三支柱 v1.0）。  

---

## 一、已定夺的总方针

| 决策 | 选择 | 理由 |
|------|------|------|
| 架构形态 | **模块化单体**（一个 FastAPI 进程） | 小团队、易部署、与现有 nginx 一致 |
| 是否微服务 | **否** | 运维心智成本高，现阶段无必要 |
| 数据库 | **SQLite 单库**（合并账号+游戏） | 已在用；日活上千前够用 |
| 实时 | **不 WebSocket** | `05` `04` 已定轮询+信箱 |
| 货币 | **仅灯油** `wallet_balance` | `23` |
| 登录标识 | **行者名 `username` 唯一**；email 可选 | `23` 减重复 |
| 世界数据 | **仓库内 JSON/YAML 配置** | 地点、物品、配方先不写后台 |
| 前端 | **延续 VitePress + 自定义 Vue 游戏页** | 不另起 React 项目 |
| Blueprint 运行时 | **MVP 不做** | 先硬编码 1～2 条订单流 |
| 同步场次 / Runsheet | **v2+** | `25` 先做订单里程碑 |
| 汇率 / 多币种 | **不做** | `23` `24` |

**一句话：一个 API 服务、一个库、配置表驱动世界、前端在 VitePress 里长游戏页。**

## 二、仓库怎么摆（目录）

```
/workspace
├── docs/                    # VitePress 站点（lore + 游戏 UI 页）
│   └── .vitepress/theme/    # 车载壳层、useAuth、后续 useShell
├── server/                  # FastAPI 游戏 API（由 auth 扩展）
│   ├── main.py              # 入口，挂路由
│   ├── db.py                # SQLite 连接、迁移
│   ├── config/              # 世界静态配置（只读）
│   │   ├── locations.json
│   │   ├── items.json
│   │   └── recipes.json
│   ├── routers/             # 按领域拆 HTTP 层
│   ├── services/            # 业务逻辑（可单测）
│   └── schemas/             # Pydantic 模型
├── data/                    # 本地开发用 sqlite（gitignore）
├── deploy/                  # nginx、systemd（已有）
└── 游戏想法/                # 设计文档（本文档索引实现）
```

**不按「前端一套、后端一套微服务」拆仓库** — 单 monorepo 即可。

## 三、后端：按功能模块拆（推荐）

### 3.1 模块一览

```
                    ┌─────────────┐
                    │   main.py   │
                    └──────┬──────┘
           ┌───────────────┼───────────────┐
           ▼               ▼               ▼
      ┌─────────┐    ┌─────────┐    ┌─────────┐
      │  auth   │    │  world  │    │  mail   │
      └─────────┘    └─────────┘    └─────────┘
           │               │               │
      ┌─────────┐    ┌─────────┐    ┌─────────┐
      │ profile │    │ orders  │    │ ledger  │
      │ wallet  │    │ shops   │    │inventory│
      └─────────┘    └─────────┘    └─────────┘
```

| 模块 | 职责 | 对应设计文档 |
|------|------|----------------|
| **auth** | 注册、登录、JWT、会话 cookie | 现有 `server/app.py` |
| **profile** | 行者名、简介、状态一句、当班开关 | `22` |
| **wallet** | 灯油余额、托管 escrow、分账 ledger | `23` |
| **world** | 地点图、打卡、区域、邻接、距离计算 | `03` `24` |
| **inventory** | 背包、穿戴槽、摆放（家园） | `18` `22` |
| **catalog** | 读 config 物品/配方百科（只读 API） | `16` `13` |
| **shops** | 开店执照、店铺、SKU 上架 | `19` `20` `21` |
| **orders** | 点菜、烹饪、配送状态机、验收 | `01` `23` `24` |
| **jobs** | 招贤帖、应聘、雇员关系 | `21` |
| **mail** | 系统信、往来信（按 user_id） | `04` `23` |
| **traces** | 地点粉笔、轻痕迹 | `03` |
| **moderation** | 敏感词、举报入口（极简） | `08` `09` v2 |

**v2 再拆：** `sessions`（场次 Runsheet）、`votes`（`14`）、`disputes`（律师团 `09`）。

### 3.2 层内约定（易维护）

```
routers/xxx.py   → 只做 HTTP：校验参数、调 service、返回 JSON
services/xxx.py  → 业务规则、状态机、调 db
schemas/xxx.py   → 请求/响应模型
db.py            → SQL；不搞 ORM 也行（SQLite 直写简单）
```

**禁止：** 在 router 里写 200 行 SQL。  
**允许：** MVP 阶段 service 里直写 SQL（比过早引入 ORM 更快）。

### 3.3 API 路径规范

统一前缀（nginx 已代理到根）：

```
/miraworld/api/health
/miraworld/api/auth/register
/miraworld/api/auth/login
/miraworld/api/me                    # 当前用户 + 钱包摘要
/miraworld/api/world/locations
/miraworld/api/world/visit/{id}
/miraworld/api/orders
/miraworld/api/shops
/miraworld/api/mail/inbox
/miraworld/api/inventory
...
```

**现有** `app.py` 迁到 `routers/auth.py`，`main.py` 聚合。

### 4.1 订单状态机（核心，写在一个 service 里）

```
created → paid_escrow → cooking → ready → delivering → delivered → confirmed → settled
                  ↘ cancelled / refunded
```

配送 MVP 可简化：`ready → delivered`（跳过骑手子状态），v1.1 再加 `delivering`。

## 五、前端：怎么长出来

### 5.1 不另起框架

| 层 | 技术 | 说明 |
|----|------|------|
| 静态 lore | VitePress markdown | 已有 |
| 车载壳 | `Layout.vue` + 底栏组件 | `05` |
| 游戏页 | `docs/miraworld/**/*.md` + Vue 组件嵌入 | 或 `docs/.vitepress/theme/pages/` |
| 状态 | composables：`useAuth`, `useShell`, `usePolling` | `05` |
| API | `fetch('/miraworld/api/...', { credentials: 'include' })` | cookie 会话 |

### 5.2 页面与模块对应

| 路由 | 页面 | 调用的 API 模块 |
|------|------|-----------------|
| `/miraworld/` | 入口/帮助 | — |
| `/miraworld/map` | 地图节点 | world |
| `/miraworld/place/:id` | 地点页 `20` | world + traces |
| `/miraworld/shop/:id` | 店铺 | shops + orders |
| `/miraworld/me` | 我的面板 `22` | profile + inventory |
| `/miraworld/mail` | 信箱 | mail |
| `/miraworld/orders/:id` | 订单详情+里程碑 | orders |

**壳层固定：** 地图 · 我要 · 信箱 · 背包 · 我的。

### 5.3 场景肖像怎么实现（易）

**服务端模板拼接**，不做 AI：

```python
# services/scene.py
ROOM_SHELLS = load_json("config/room_shells.json")
def portrait_room(room_id, placed: list[PlacedItem]) -> str:
    lines = [ROOM_SHELLS[room_id]]
    for slot, item in placed:
        lines.append(ANCHOR_TEXT[room_id][slot].format(flavor=item.flavor))
    return "\n".join(lines)
```

前端只渲染返回的字符串。

## 六、分阶段实现（严格砍 scope）

### Phase 0 — 现状 ✅

- VitePress 站点、auth API、nginx 部署

### Phase 1 — 能逛世界（约 1 个里程碑）

- [ ] 合并 DB；`username` 注册登录
- [ ] `locations.json` 5 个节点 + 访问打卡变色
- [ ] `/me` 钱包 100 灯油新手赠送
- [ ] 地图页 + 地点页（静态描述 + 打卡 API）
- [ ] 壳层底栏骨架

**不做了：** 订单、店铺、邮件

### Phase 2 — 能点一碗面（核心竖切）

- [ ] `items.json` + `recipes.json`（面、面粉、酱油）
- [ ] 1 个系统店铺 + 1 个 SKU
- [ ] 下单 → escrow → 厨师（店主 NPC 或自己点自己店测试）→ 扣料 → 出餐 → 入背包
- [ ] `order_events` 里程碑展示
- [ ] 分账 ledger（店主+平台）

**不做了：** 配送、招聘、骑手

### Phase 3 — 能开店请厨师

- [ ] 开店考（静态题 JSON）+ `shops` 表
- [ ] 玩家开店、上架 SKU
- [ ] `shop_employees` + 按单分成
- [ ] 招贤帖 + 应聘 + 信箱通知
- [ ] 离线自动当班 v1（`27`）：日程开关 + 厨师自动接单烹饪；v1.1 自动采购

### Phase 4 — 能送到家

- [ ] `homes` + 锚点 location
- [ ] 图距离运费公式 `24`
- [ ] 配送子单（可系统馆驿卒托底）
- [ ] ETA 文案字段

### Phase 5 — 丰富度（按需）

- 痕迹、悬赏栏、投票、律师、session/Runsheet…

**每个 Phase 结束应能演示一条完整用户故事。**

## 七、配置驱动 vs 代码写死

| 数据 | MVP 做法 |
|------|----------|
| 地点、边、区域 | `config/locations.json` |
| 物品、标签 | `config/items.json` |
| 配方 | `config/recipes.json` |
| 开店考题 | `config/merchant_exam.json` |
| 房间空壳文案 | `config/room_shells.json` |
| 敏感词 | `config/banned_words.txt` |

**改世界不用发版后端逻辑** — 改 JSON + 重启（或热加载）。

玩家自创 T2 物品、地图新节点 — **v2** 再做审核入库 API。

## 八、横切关注点（各模块共用）

|  concern | 做法 |
|----------|------|
| 鉴权 | 依赖 `get_current_user()`；cookie JWT 沿用 |
| 幂等 | 订单状态转移检查 `current_status` |
| 事务 | 扣款+建单同一 SQLite transaction |
| 错误 | HTTP 4xx + `{ "detail": "..." }` |
| 日志 | 订单/ledger 写库即审计；文件 log 可选 |
| 测试 | 每 module 至少 1 个 pytest：下单分账、余额不足 |

## 十一、小结（给你拍板的结果）

| 问题 | 定夺 |
|------|------|
| 程序怎么写？ | **FastAPI 模块化单体**：routers + services + SQLite |
| 是否按功能分模块？ | **是**，按上表 10 个领域模块；**不是**按微服务拆进程 |
| 前端？ | **VitePress + Vue 游戏页**，不新开框架 |
| 先做啥？ | **Phase 1 地图 → Phase 2 一碗面** |
| 什么后做？ | 配送、招聘、场次、律师、Blueprint |
| 世界内容？ | **JSON 配置**，不做 GM 后台 |
| 最难的订单？ | **一个 orders service 状态机** + **ledger 分账** |

> 模块要分得清，部署要剩一个包；  
> 第一口能吃的，是地图上走五步、店里点一碗面——  
> 其余设计文档，按 Phase 排队进场。
