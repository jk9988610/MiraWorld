# 异步通讯：像邮箱，不像聊天室

> 状态：社交与通讯构思  
> 记录时间：2026-09-12  
> 来源：与作者的讨论  

---

## 一、一句话

全球玩家**很难同时在线**，实时聊天也不适合小团队维护的服务器规模。  
本作默认 **异步通讯**：像邮箱一样写信、收信、**过一阵子再回复**——不追求秒回，不假装大家都在。  
许多体验也倾向异步，用「先后往来」营造**有人曾在这里**的感觉，而不是硬做实时同屏。

---

## 二、为什么要异步优先

### 2.1 现实约束

| 现象 | 对实时互动的打击 |
|------|------------------|
| **时区相反** | 你白天在线，对方在睡觉；能碰面的窗口极窄 |
| **服务器规模小** | 很难维持大频道、大房间、全球低延迟同步 |
| **网页文字向** | 玩家常碎片时间打开，不是挂机 MMO |
| **「向往同时在线」** | 情感上想要「有人在」；技术上却**极难稳定做到** |

若把核心社交绑在实时聊天上，大多数人会对着**空频道**或**已离线的人**说话——体验比没有还差。

### 2.2 设计立场

> **不假装世界此刻挤满了人；承认大家错开时间，仍能让往来有意义。**

异步通讯满足：

- 发信时不必对方在线  
- 收信者在自己的时间段打开、阅读、**回复**（回复同样异步）  
- 对话是**线程**（信串），不是必须盯着的聊天窗口  

这和 [03-地图打卡与异步痕迹](./03-地图打卡与异步痕迹.md) 同一套哲学：**先后顺序**，不是**同一时刻**。

## 三、通讯模型：邮箱，不是聊天室

### 3.1 和「系统邮箱」的关系

[02-点菜式成长](./02-点菜式成长.md) 里已有 **系统邮箱**（奖励、成就庆祝、公告）。  
玩家之间的往来，建议用**同一套「信箱」心智**，但分栏或分类型：

| 信箱类型 | 方向 | 典型内容 |
|----------|------|----------|
| **系统信箱** | 系统 → 玩家 | 奖励、成就庆祝、馆规、更新说明 |
| **往来信箱** | 玩家 ↔ 玩家 | 私信、订单沟通、委托函往来 |
| **（可选）势力/店铺信箱** | 组织 → 订阅者 | 仅对已订阅者；仍建议异步，不弹窗催 |

UI 可以是一个「信箱」入口，内分 Tab；玩家学一次心智即可。

### 3.2 一封信的生命周期

```
A 写信给 B（B 离线）
        │
        ▼
服务器存信，标记 B 信箱「未读」
        │
        ▼
B 某日上线，打开信箱，读到 A 的信
        │
        ▼
B 点「回复」→ 新信进入 A 的往来信箱
        │
        ▼
A 下次上线时看见回复（不必秒回）
```

- **无「对方正在输入…」**  
- **无强依赖 WebSocket 长连接**（未读角标可用轮询或轻量通知，仍遵守订阅前零推送）  
- 订单、商单协商、厨师与食客沟通 —— **优先走往来信箱**，留下可查证记录  

### 3.3 和实时聊天的边界

| | 异步往来信箱 | 实时聊天（若将来有） |
|--|----------------|----------------------|
| 默认 | **是** | 否 / 极弱化 |
| 时区 | 友好 | 不友好 |
| 服务器 | 存信 + 读信，简单 | 房间、在线状态、广播 |
| 商单纠纷 | 有信串记录 | 难举证 |
| 氛围 | 书信、委托函 | 喧闹频道 |

**MVP 建议：不做全服实时公屏聊天。** 若以后要做，仅限小范围（公会内部、同订单临时线程），且仍不替代往来信箱。

## 四、「伪同时在线」：用异步营造存在感

玩家会**向往**「世界里有别人」，但全球错时让**真·同时在线**很难。用异步层叠出类似感受：

| 手段 | 玩家感受 | 是否实时 |
|------|----------|----------|
| [地图痕迹](./03-地图打卡与异步痕迹.md) | 「有人来过、留过字」 | 否 |
| 往来信箱 | 「有人给我写过信」 | 否 |
| 悬赏栏 / 订单池 | 「有人在发单、接单」 | 列表异步刷新即可 |
| 店铺评价、足迹统计 | 「很多人买过 / 到过」 | 否 |
| 在线人数显示 | 易造假、易落空 | 可选弱化或不做 |

**不追求**虚假的全服「9999 人在线」；**追求**打开信箱或地图时，能看见**真实的、有时间戳的**他人痕迹。

## 五、体验全面倾向异步（不限于聊天）

以下玩法都可按异步设计，减轻「必须凑人同时在线」的压力：

| 场景 | 实时做法（难） | 异步做法（推荐） |
|------|----------------|------------------|
| 委托调查 | 两人语音同步跑图 | 食客点单 → 厨师异步完成 → 信箱交付摘要 |
| 护送 | 必须同屏 | 订单状态机 + 里程碑信（「货已至 X 站」） |
| 交易议价 | 当面交易 | 往来信箱报价 / 订单改价请求 |
| 协作编剧 | 同文档实时编辑 | 版本提交 + 信箱审阅意见（后期） |
| 世界事件 | 全服同一分钟打 BOSS | 贡献累计条 + 结束后全服结果公告（邮箱/公告栏） |

原则：**硬状态（钱、货、任务完成）服务器算；软沟通（商量、叙事）信箱传。**

与 [01-任务拆分与悬赏派发](./01-任务拆分与悬赏派发.md) 一致：订单内核 + 事件溯源，比聊天截图可靠。

## 六、馆规与防滥用

| 风险 | 对策 |
|------|------|
| 骚扰私信 | 陌生人首信限制、拉黑、举报；可关「接受陌生人来信」 |
| 诈骗 | 馆规提示：敏感交易走订单托管，不信信箱里线下转账 |
| 垃圾信 | 频率限制、信誉门槛、新号冷却 |
| 未成年人 / 合规 | 留存信串供申诉；敏感词与审核策略待定 |
| 订阅前推送 | 往来信**不进浏览器推送**；仅信箱未读角标（见 02） |

## 七、技术草图（轻量即可）

```text
messages
  id, thread_id, from_user_id, to_user_id,
  subject, body, created_at, read_at

threads（可选，把来回归一串）
  id, participant_ids[], last_message_at, context_type, context_id
  -- context: order_id / bounty_id / null（纯私信）
```

- **写入**：HTTP POST 发信  
- **读取**：打开信箱时分页拉取；标记 `read_at`  
- **回复**：同 `thread_id` 追加 `messages` 行  
- **不必**为聊天单独维护在线表；可选 `last_seen_at` 仅用于展示「许久未见」，不承诺实时  
- 未读角标：**慢轮询** + 打开信箱全量拉取（见 [05-车载式界面与状态刷新](./05-车载式界面与状态刷新.md)）

扩容时与 `03` 相同：**无状态 API + 共享库**，信存在用户维度，不按物理机分服。

## 八、MVP 可验证什么

1. **往来信箱**：A 发信 → B 离线 → B 上线读到 → B 回复 → A 再读到  
2. 与 **系统信箱** 分 Tab，奖励信仍手动领取  
3. 绑定 **一笔订单**：订单详情页「发信给对方」，信串带 `order_id`  
4. **不做**全服实时公屏  
5. 问玩家：异步回信是否比空聊天频道更有「真的在和活人往来的」感？

## 十、小结

| 旧默认 | 本作 |
|--------|------|
| 实时聊天是社交核心 | **往来信箱**是默认；有回复，无秒回 |
| 全球同服同时在线 | **错时友好**；用痕迹、信串、订单池营造存在感 |
| 向往「有人在」→ 造假在线数 | **向往「有人来过」** → 真异步记录 |
| 玩法要凑同时在线 | **玩法倾向异步**；硬结果服务器算，软沟通信箱传 |

> 世界像跨时区的邮局：你留一封信，对方睡醒后拆开，再回一封。不必同在灯下，往来仍然成立。
